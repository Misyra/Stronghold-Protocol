# 同站同盟匹配

在游戏的“选择模拟协议”页选择“同盟匹配”，选择实际游戏难度，再点击“开始匹配”。
队列仅包含当前游戏服务端进程内主动匹配的真人，按难度分组、先到先配。
预组队的同盟以整队入队（等待室里的“同盟匹配”），队伍人数算作已占的席位数；单人入队、人数够了再补进预组队。
凑齐四人后进入确认：每人有 30 秒点“确认入场”，全员确认才创建同盟并进入本局信息确认（之后策略选择、机变、休整期照常），不添加 AI，也无需重新准备。
有人取消或超时没确认时，这次配对作废，其余人的队列位置保留，继续等下一轮。
等候时可查看人数、时长并随时取消；排队超过 10 分钟仍未凑齐会自动结束并提示。
断线即退出队列，重新连接后须再次点击匹配。
普通创建房间、加入房间也会退出匹配队列；已在房间中的玩家须先离开房间才能匹配。

服务端沿用房间总数与每地址的开局上限（`maxRooms`、`maxMatchesPerAddr`）。
分配房间失败（房间数到顶、地址超限、维护中、开局校验没过）时已经分配出去的房间会收回，队伍留在队列里等下一次机会，不需要重新排队。
队列保存在内存中，重启后清空。一个站点若部署多个独立游戏进程，队列不会跨进程共享。

## 开发者控制台与匹配互斥

同盟房里打开开发者控制台（`room.console.enable`）之后，这间房就不能进匹配队列：服务端回 `ERR.CONSOLE_ON`（「房间已开启开发者控制台，无法进入匹配队列」）。
客户端把代价说在前面：

- 开机那一刻弹一条 5 秒警告「开发者控制台已开启：本房间不会进入匹配队列」——开关在 ⚙ 弹层里，离「开始搜寻」很远。
- 「开始搜寻」留在原位、置灰，悬停显示拒绝原因，而不是点下去才被服务器拒。
- ⚙ 弹层里开关下方常驻一句「不能进入匹配队列」，随时看得出房间为什么不排队。

关掉控制台即可恢复排队。反向规则不变：房间在排队时不能开控制台（`ERR.QUEUED`）。

## 中间页接入

中间页保持独立项目 `sp-portal`，不承载游戏匹配队列。
`GET /api/rooms/:CODE/status` 原本已有 `difficulty`，本次增加 `difficultyName`。
难度为游戏实际定义：`FUNNY` 标准模拟、`NORMAL` 险境模拟、`HARD` 绝境模拟、`ABYSS` 终极模拟。
中间页读取此接口，不接受提交者指定难度。

游戏新增无会话的 `GET /api/ping`（支持 HEAD、OPTIONS，公开 CORS），供独立中间页测量浏览器到游戏站点的 HTTP 往返延迟。
它包含网络和 HTTP 服务响应时间，不等同于游戏 WebSocket 延迟。
每个站点最多每 30 秒探测一次，5 秒超时。演示模式不探测真实站点，也不伪造延迟数值。
上线时需更新游戏服务端及客户端；站点的反向代理应将 `/api/ping` 转发到游戏服务端。
旧服务端尚未提供此接口时，中间页会显示探测失败。

游戏服务端验证：`node --import ./test/helpers/test-setup.js --test test/matchmaking.test.js test/matchmaking-party.test.js test/lobby.test.js test/lobby-loadout.test.js`。
浏览器验证（本机 Chrome）：设置 `SP_E2E=1`、`CHROME_PATH` 后运行 `node --import ./test/helpers/test-setup.js --test test/ui/matchmaking.e2e.test.js`（包含四人全员“确认入场”那一步）。
