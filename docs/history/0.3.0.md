# DESIGN §32 — 0.3.0-dev

Part of [DESIGN.md](../DESIGN.md). The plugin system (插件).

## 32. The plugin system

Unreleased. The owner decided on 2026-10-12 that the plugin system is the 0.3.0 release. Its design study (the
maintainers' notes of 2026-10-12) proposed a phased plan; the owner adopted its recommendations with the decisions
below. This chapter records what each phase changes; the reference is [PLUGINS.md](../PLUGINS.md).

### 32.1 Decisions and phases

The owner's decisions (2026-10-12):

- **MVP:** cosmetic plugins (art) and data plugins, the host's switches in the room, a content hash that every client
  checks — and **no third-party code**. Code comes later in steps, each a decision of its own: a declarative DSL, then a
  sandbox, then trusted code with the explicit consent of the server owner and of every player.
- **Position:** the original game is always the default; plugins are marked **unofficial** everywhere; plugin matches
  stay out of the statistics overview by default — those with plugins that change gameplay: a match with only cosmetic
  plugins counts as the original game (the owner's decision of 2026-10-13, §32.3); bugs seen in a plugin room go to the
  plugin's author first; no plugin
  overrides arbitrary project files; the interface word is 「插件」 (never 「模组」, which names the operators' modules).
- Everything else as the study recommended: plugins are installed on the server only and chosen by the room's host
  (gameplay) or by a player for themself (cosmetics); `plugins/<id>/plugin.json`; `packs/` keeps working; one content
  set per room with a worker per modded set; per-plugin, per-room and concurrent-set limits; incompatible gameplay
  plugins refused by default; no official files distributed through plugins.

| Phase | Content | State |
|---|---|---|
| P0 | content identity and the plugin registry, no change for players | §32.2 |
| P1a | cosmetic plugins (room and personal) | §32.3 |
| P1b | data plugins: patches, compact records, kitRef / SkillSpec operators, modes, i18n | planned |
| P1c | per-room content sets: the host's 插件 panel, a worker per set, the client loading and checking `/cs/<cs>/`, the unofficial marks | planned |
| P2, P3, P4 | DSL-lite; one script API, trusted then sandboxed; interface plugins | later decisions |
| studio | the plugin studio and the authoring tools (part 1: cosmetic plugins, the error catalogue, schemas, hot reload) | §32.9 |

### 32.2 P0 — content identity and the registry

Seen: the design study's §6.1 and its "P0 基础" list. Nothing a player sees changes; the golden results are byte for
byte unchanged (no scenario moved).

**The content hash.** `cs` names the content a room plays (`shared/plugins/identity.js`):
`sha256(canonical({ v: 1, app, sim, data, plugins, settings }))`. `sim` hashes the sorted `[path, sha256]` list of
every served `/sim/**.js` (not `nodeData.js`), `/shared/**.js` and the `/data.js` stand-in; `data` maps every gameplay
`data/<name>.json` to its hash — every file `server/data.js` loads but the presentation files `assets`, `local-assets`
(this machine's extracted art) and `emotes`, and not `data/i18n/` — so any code or data change yields a new `cs` and a
machine's own art does not. `plugins` is `[]` and `settings` `{}` for the vanilla content. `canonical` sorts keys and
drops white space; the bytes are the served bytes (a patched file, P1b: the JSON text served from memory), so a browser
hashes what it received. `shared/sha256.js` is SHA-256 in plain JavaScript: the same digests in Node and every browser,
also where `crypto.subtle` is missing (a LAN address is no secure context); the server hashes file bytes with
node:crypto and the tests check that both agree. `.gitattributes` already checks code and data out with LF, so a
Windows clone has the same `cs`. The server computes it once at start (`server/plugins/identity.js`; like the build
tag, a file changed afterwards counts from the next start) and logs `[content] vanilla <16 hex>`.

**Where it shows** (normative: design/network.md §8.4): `welcome.content { vanilla }`; `room.state.content { cs,
vanilla: true, plugins: [] }` — always the vanilla set in P0; the lobby hands `cs` to the match (`opts.cs`, the MATCH
INTERFACE), which copies it into every BattleSpec (`buildBattleSpec` keeps a well-formed `cs`, drops anything else;
`createBattleFromSpec` never reads it — a spec built without one is what it always was); `b.result.cs` is optional and
checked for its form only (the comparison is P1c's); `/healthz content { vanilla, sets: 0 }`; `GET
/cs/<16 hex>/index.json` — the manifest of the content set (every code file's hash, every data file's URL with `?v=`,
hash and size), cached for good, 404 for any other `cs`; the diagnostics' second line `content: vanilla cs=<64 hex>`
(`public/js/diag.js contentLine`; the client keeps `welcome.content` in its store; a plugin room will read `MODDED cs=…
plugins=id@version(hash)…`). The player guide's diagnostics paragraph names the line.

**The registry.** `server/plugins/registry.js` scans the language folders, `packs/` and `plugins/` and answers
`/packs/index.json` exactly as before (the language menu is unchanged), `/packs/<id>/<file>` (only what a lang
manifest names) and the new catalogue `GET /plugins/index.json` (`{ version, app, api, content: { vanilla }, plugins }`,
never cached: every plugin and pack by class with its status, the `unofficial` mark on every class but `lang`, public
manifest fields, size, file count — never a server path). `server/packs.js` is a compatibility export of it;
`shared/packs.js` keeps the language-pack index and forwards the manifest helpers (`PACK_TYPES` now carries each
type's plugin class: `assets` → `cosmetic`, `data` → `content`). Only the class `lang` loads in P0 (a lang plugin of
`plugins/` is a language entry like a pack folder in the live server's index; `tools/packs.mjs` — whose static index
could not serve a plugin's files — and `tools/i18n.mjs` keep reading the language folders and `packs/` only);
`cosmetic` and `content` plugins are checked and listed as `planned`; `script`, `ui` and `trusted` as `unsupported`,
never loaded. Folders starting with `_` (templates) and files at the top of `plugins/` are never read; a duplicate id
(across `packs/` and `plugins/`, any case) or language, a broken manifest, a disallowed file or a link inside a folder
keeps an entry out with a reason; a missing or out-of-range `requires` is a warning (P1c refuses to enable it).

**Manifest 2** (`shared/plugins/manifest.js`; reference PLUGINS.md §3–§5): `manifest: 2`, the id from the folder
(`^[a-z0-9][a-z0-9-]{1,31}$`), localized name / description, semver `version`, `app` range and `api` level (both
required but for `lang`; `PLUGIN_API = { current: 1, min: 1 }` in `shared/constants.js`), `class`, `scope` by class,
dependencies and ordering hints, typed settings (no free text), permissions that must match the parts, the parts
(`assets`, `theme`, `data`, `operators`, `enemies`, `modes`, `stages`, `dsl`, `i18n`) and entry points by class; the
file rules by class (no SVG, code only in code classes, documents never served) and the limits. Manifest 1 is read
exactly as in 0.2.0 (`readPackManifest`; `normalizeManifest` forwards to it).

**Tools, git, packages.** `node tools/plugin.mjs list` (by class, the skipped and why, the vanilla `cs`) and `check`
(manifest, files, paths, every JSON file's validity, nesting and numbers; exit 1 on a problem, `--strict` on a
warning). `.gitignore` ignores `plugins/*` but `plugins/README.md` and `plugins/_template/` (the templates come with
P1: each class's inner formats are P1a's and P1b's); the release zips ship the tracked ones (`tools/package.mjs`
`RUNTIME_DIRS`), never a server's own plugins; an update never touches them. An entry that cannot be read at all (say,
JSON nested too deep to quote back) is skipped with its reason and never stops the scan or the server's start.

[ASSUMED] — the study's own assumptions and the choices of this step, for the owner to confirm or change:

- every limit (8 MB per JSON file, nesting 64, numbers ±1e9, 200 MB and 5000 files per plugin) and `PLUGIN_API`;
- the id rule, and that `app` and `api` are required for every class but `lang`, `version` must be semver, and a
  numeric setting needs `min` and `max`;
- the presentation files left out of `cs` (`assets`, `local-assets`, `emotes`) and that every other `data/*.json`
  counts (a new gameplay file is included without a code change);
- 16 hex digits in URLs, 8 in the interface, 64 in reports; `/healthz content.sets` counts the modded sets in use;
- the registry checks manifests, file types, sizes and paths whenever it scans, but parses the JSON contents only in
  `tools/plugin.mjs check` (the content set builder of P1b parses and validates what it applies);
- a lang plugin may live in `plugins/` (manifest 2) as well as in `packs/` (manifest 1);
- a symbolic link inside a plugin folder keeps it out (a plugin folder that is itself a link is fine); dot files are
  ignored and never served.

Tests: `test/plugins/manifest.test.js`, `test/plugins/registry.test.js`, `test/plugins/identity.test.js`;
`test/diag.test.js` (the content line); still green: `test/i18n-packs.test.js`, `test/check-imports.test.js`, the
golden results. Normative lines rewritten: design/network.md §8.1 (welcome / room.state additions), §8.4 (new), §14
(BattleSpec `cs?`, `b.result { …, cs? }`).

### 32.3 P1a — cosmetic plugins

Seen: the design study's §3.1, §4.5, §6.1–§6.3, §7.1, §7.4, §7.5, §9.4 and its "P1a 外观" list. A cosmetic plugin changes
what the game shows and plays — avatars, portraits, Spine models, icons, interface pictures, voices, sound effects,
music — never a battle (the simulation reads data, not art), so a room's `cs` stays the vanilla one whatever its art.
With no plugin switched on nothing changes: the room's content is exactly P0's `{ cs, vanilla: true, plugins: [] }`, the
served manifests are byte for byte those of 0.2.6, and the golden results are unchanged (no scenario moved). The
reference is PLUGINS.md §9.

**The overlay** (`shared/plugins/visual.js`): the manifest's `assets` part, inline or a `.json` file, in the shape of
`data/assets.json` — the record containers `chars` (`avatar`, `avatarE2`, `portrait`, `portraitE2`, `spine.front`,
`spine.back`), `enemies` (`icon`, `spine`), `tokens` (`avatar`, `spine`), `bonds` / `items` / `bands` / `skills` /
`modules` / `ui` and `prof.*` (an image), `audio.bgm` (the named tracks) / `audio.bossBgm` (a track `{ loop, intro? }`,
written whole), `audio.voice` / `voiceJp` (a file or a list per slot), `audio.sfx.ui` / `battle` / `units`. A value is a path inside the
plugin folder of the field's kind (`.png .jpg .webp`, `.mp3 .ogg`), a Spine model `{ skel, atlas, textures, pma }` (the
atlas next to the skeleton with its name, the pages inside its folder) or a reference `{ "ref": "<key>" }` to the entry
of the same container in the installation's manifest — a whole record (replaced as a whole; keys beside the `ref` change
fields of it) or one field. A missing entry is a problem; another section or field is a warning and left out; nothing
but URLs and a model's clip data is ever written into the manifest. A field a plugin does not write keeps the
installation's value; a track is written whole (no installation intro before a plugin's loop); a model written for an
enemy or a token takes away its local-client model `spineLocal` (the client draws that one first) — an implied write,
never reported as an override of its own. A write to an entry the installation has needs
`assets.override`, a new entry `assets.add`. The overlay becomes a list of writes (`ops`) in the plugin's order;
resolved, a file is `/p/<id>/<8 hex>/<path>` (the first 8 hex digits of its SHA-256 — of its model's files' SHA-256s for
every file of a Spine model, so pixi-spine finds the atlas and pages beside the skeleton), a reference the entry's value
in the manifest it is resolved against (the served one). `applyOps` writes each value whole, copying the objects on the
way; `mergePluginOps` keeps the load order — the later plugin wins — and reports every path two plugins change (the
same, or one inside the other: `override { path, plugins }`). `theme` is not applied (a warning); fonts are not part of
the overlay.

**The load order** (`shared/plugins/order.js`, the study's §4.8): a plugin's `requires` join the set (`auto`) when they
may (installed, loaded, of the class and scope, in range) — else PLUGIN_DEPENDENCY; a `conflicts` in range with another
plugin of the set is PLUGIN_CONFLICT; requires / optional / loadAfter put a plugin after, loadBefore before; among the
plugins free to go, the higher `priority`, then the lower id; a cycle is PLUGIN_DEPENDENCY.

**Spine models**: their clip roles, durations, events, hit times and bounds come from `plugin.lock.json`, written by
`node tools/plugin.mjs pack <dir>`, which parses each skeleton the way `tools/fetch-assets.mjs` parses the game's
(`tools/assets/skel.mjs`, `anim-roles.mjs`; an operator's three skill slots, an enemy's numbered skills — both for a
skeleton both use), checks the atlas pages against `textures`, and adds every file's SHA-256 and size; an overlay
problem (a reference the manifest lacks) leaves the lock unwritten. A lock made from another skeleton (its SHA-256) is a
problem. The server rebuilds the lock's clip data in the shape the tool writes (`readPluginLock`: the known roles, every
clip they play an animation of the skeleton, ≤ 256 animations and 64 events, names ≤ 64 characters, durations and hit
times ≤ 600 s, bounds as four numbers; depth ≤ 64; maps without a prototype), so nothing a hand-made lock adds reaches a
browser (review of 2026-10-12: a hand-made lock used to pass any role, name or nesting through to every client, and a
deeply nested one made the room's documents fail). `tools/assets/skel.mjs parseSkel` copies a buffer that is a view into a larger one first (the Spine runtime
reads `.buffer` from its start; a small file read with `fs.readFileSync` comes from Node's pool) — the game's own models
are read as before.

**The registry** (`server/plugins/registry.js`) loads the class `cosmetic` now (`status: 'loaded'`; the pack view's
`supported` stays the lang class): when it scans it reads a cosmetic plugin's overlay and lock, checks them against this
installation's `data/assets.json` (read only when a cosmetic plugin needs it), counts what its references copy out of it
(≤ 2 MB), and hashes the files that shape it (SHA-256, kept by path + size + mtime across scans); a problem keeps the
plugin out like any other. Its folder signature now looks six levels deep (a model's files sit at
`spine/<model>/front/…`) and includes `data/assets.json`'s size and time (a manifest rewritten while the server runs is
read again). `pluginFile(id, path)` is the whitelist of `/p/`; `rescan()` reads the folders again however
they look. A catalogue entry of a loaded cosmetic plugin adds `vs` (the set of it alone) and `artBytes`.

**The visual hash** `vs = sha256(canonical({ v: 2, assets: <SHA-256 of data/assets.json>, overlays: [{ id, version, files,
writes }] }))` (the study's §6.1), `files` mapping every file that shapes a plugin's overlay — `plugin.json`, the lock, the
`assets` file, every file the overlay serves — to its SHA-256, `writes` the SHA-256 of the plugin's writes as served
(round 3, §32.3.2: `vs` pins which file goes to which slot).

**The visual sets** (`server/plugins/visualSet.js`): `resolve(ids, { scope })` — loaded cosmetic plugins of the scope,
closed and sorted, ≤ 300 MB of art and ≤ 4 MB copied by references (PLUGIN_UNKNOWN / PLUGIN_BLOCKED / PLUGIN_DEPENDENCY /
PLUGIN_CONFLICT / PLUGIN_LIMIT otherwise) — names the set by its `vs` and keeps it: a room holds its set while it uses it
(`hold` / `release`, never dropped meanwhile), of the others the 256 most recently used stay (a plugin's own set is known
from the catalogue). Its document: `GET /vs/<vs16>/overlay.json` — `{ visual: { v, vs, assets, overlays }, writes: [{ id,
ops }] }`, the composition and each plugin's writes in its own terms (paths of its folder, references, a model's clip
data), never a URL nor a copy of the art manifest; `no-cache` with the body's hash as ETag (the last 8 built are kept; a
document is built once however many ask). `GET /p/<id>/<hash8>/<path>` (`server/http/static.js`) serves only a file a loaded cosmetic
plugin's overlay names — not `plugin.json`, the lock, a document or another file of the folder, no dot file, no `..`, no
real path out of the folder (checked again when served: a link put in later is not followed) —, `immutable` at the hash
of its bytes (its own, or its model's), the current file with `no-cache` at any other (as `/assets/~<hash>/` does); a
file found changed has the registry read the folders again (at most every 5 s). In the traffic counters `/p/` counts as
assets (audio for `.mp3` / `.ogg`), `/vs/` as data.

**The room** (`server/lobby.js`, design/network.md §8.4): `room.setPlugins { plugins: [{ id, settings? }] }` — host-only,
before the match (ROOM_STARTED), in the heavy rate-limit bucket (`server/net.js HEAVY_TYPES`), and like a difficulty change
it un-readies the other humans; the same set again changes nothing, and when only its 「自动」 marks change (a plugin first
switched on automatically, now chosen) the state is broadcast without un-readying. The room holds its set in the visual
sets until it changes or the room goes. The room's content becomes `{ cs, vanilla: true, vs, plugins: [{ id, version, class: 'cosmetic', hash, auto? }],
warnings, bytes }`: `cs` stays the vanilla one, so the match receives the vanilla `cs` and its BattleSpecs are those of
the original content; an empty list brings back exactly the vanilla shape. The set is the room's: kept across its matches
and a host change. `settings` is read by the classes that have settings (none of a cosmetic plugin). New ERR codes, in
every language pack: PLUGIN_UNKNOWN, PLUGIN_BLOCKED, PLUGIN_DEPENDENCY, PLUGIN_CONFLICT, PLUGIN_LIMIT.

**The browser**: `public/js/content.js` follows `room.state.content.vs` — it fetches `/vs/<vs16>/overlay.json` as text,
parses it, checks that its composition hashes to the room's `vs` (`checkVisualDoc`) and makes it the room layer
(`public/js/assets.js` cosmetic layers: the installation's manifest → the room's set → the player's personal plugins),
composed on the manifest the page loaded itself: every plugin URL built from the composition's file table, every
reference copied out of the page's manifest, a write that does not fit left out (`shared/plugins/visual.js`
prepareVisualDoc / layVisualOps — review round 2, §32.3.1); leaving the room, or a room without plugins, takes the layer
away — one room's art never stays behind or piles up. data.js shows `assets` through the layers (`setView`), so every `data.get('assets')` of the interface, the audio and
the asset store the renderer uses (seeded with the manifest as downloaded, laying the layers over it itself) draw the
room's art; a layer change is told like a late manifest. A document that fails or will not download (two retries) leaves
the original art and says so once (a toast; an attempt is given up after 30 s). The room's top bar shows 「原版」 or
「插件 ×N」, which opens the 插件 panel (`public/js/ui/pluginPanel.js`: the server's cosmetic plugins of scope `room` with
the host's switches — read-only for the others and during a match —, versions, authors, sizes, 非官方, 「自动」, a note for
one made for other game versions, the override warnings; a room plugin the server no longer offers stays by its id, its
switch only turning it off, and is never sent again). 设置 → 外观插件 switches the server's cosmetic plugins of scope `personal` for this browser only
(`localStorage` `sp.pref.cosmetics`): each is fetched as `/vs/<vs16>/overlay.json` of its catalogue `vs` (side by side),
checked, and laid over whatever the page draws. The layers keep the manifest they make per base object (data.js's copy
and the renderer's store's may be two). The title screen says 「本服务器安装了 N 个插件」 when the catalogue lists unofficial
plugins (a button: their list, what this version does with each). The diagnostics' content line: `vanilla cs=… cosmetic
vs=… plugins=id@version(hash),…` in a room with cosmetic plugins, ` personal=id,…` for the player's own.

**Template and tools**: `plugins/_template/cosmetic/` (references only — no file of the game; the folder name is the id);
`node tools/plugin.mjs pack <dir>` (above); `check` follows a cosmetic plugin's references to the checkout's
`data/assets.json`.

**Statistics** (the owner's decision of 2026-10-13): a match whose plugins are all cosmetic plays the vanilla `cs` and
counts as the original game in the statistics overview (`room.state.content.vanilla` stays `true`) — its gameplay and
numbers are the original ones, and a player's personal cosmetics never matter; only matches with plugins that change
gameplay are left out (with P1b / P1c). Every stats record names the room's `vs` (round 2).

### 32.3.1 P1a — review round 2

An independent review (2026-10-12) found what P1a had left loose; the changes, each a decision of this step:

- **The browser composes the art itself** (it was handed a manifest the server put together): `/vs/<vs16>/overlay.json`
  carries the set's composition and each plugin's writes in the plugin's own terms (paths of its folder, references, a
  model's clip data) and no URL; `/vs/<vs16>/assets.json` is gone. The page builds every plugin URL from the
  composition's file table — the very table `vs` hashes —, copies every reference out of the manifest it loaded itself
  (`/data/assets.json`, 0.2.6's `/assets/~<hash>/` URLs), lays the plugins in the composition's load order, and leaves
  out what does not fit: a file the table lacks or of another kind than its field, a path outside the containers, a
  model out of its folder or of the lock's shape, a reference its manifest lacks (`shared/plugins/visual.js`
  prepareVisualDoc / layVisualOps; one toast per page). What it draws is exactly what `vs` names, and a room's set costs
  a few KB instead of the 1.3 MB manifest. (The point is consistency and bandwidth, not defence against the server.)
- **`/p/` serves only the very file the scan hashed**: the request `lstat`s the path — a symbolic link put in place of a
  served file after the scan is refused (404) wherever it leads, another file or a dot file of the folder included —
  and wants the real path the scan recorded (a link put in place of a folder on its way is refused too).
- **A file is the hashed one while it keeps its size, mtime, inode and ctime** (`registry.js statIdentity`): one rewritten
  with its old size and mtime put back (`rsync -t`, `touch -r`) is no longer served `immutable` under its old hash —
  `no-cache`, and the registry reads the folders again and hashes it again (its hash cache keys on all four).
- **`room.setPlugins` drops the host's result replay only when the set changed** — its `vs` or its 「自动」 marks: the
  same set again, or a refused one, leaves a settlement screen that is still open.
- **A plugin's audio is fetched without its extension**, like the installation's through `/media/` (download managers
  pop up a dialog for every fetch ending in `.mp3`): `/p/<id>/<hash8>/<path without .mp3 / .ogg>` serves the listed
  audio file of that name — of a `.mp3` and a `.ogg` of one name, the one whose hash the URL names — with the same
  whitelist and cache rules (`server/http/static.js`); `public/js/media.js mediaUrl` maps a plugin's audio URL to it and
  `public/js/audio.js` keeps its fallback to the URL with the extension. The traffic counters count it as audio.
- **A plugin file that will not load falls back, per entry**: an `<img>` of the interface (one capture listener for the
  page, `public/js/content.js`), a picture or a Spine model of the board (`public/js/assets.js` reports its own failures
  — a model not while the tab is hidden: a load the hidden tab left hanging is not the file's fault, GitHub #68), the
  shadow sprite, a sound (`public/js/audio.js` onFailed, wired in `main.js`) → the cosmetic layers leave the writes with
  that URL out (`createCosmeticLayers fail`), so the entry draws the art beneath it — the installation's, or the room's
  under a personal plugin — for the rest of the page's life [ASSUMED], the views re-resolve it (above), and a sound plays

### 32.9 The plugin studio and the authoring tools

The owner's decision of 2026-10-13 (the 0.3.0 plan): every authoring tool of the design study's §8 ships with 0.3.0, the
first part here — someone who does not write code makes, previews and packs a cosmetic plugin in the browser; someone who
does gets a schema, findings in plain words and hot reload — and the packer does **not** screen for official game files
(what a plugin carries is its author's responsibility; PLUGINS.md §1 still asks never to put them in). The data, DSL,
script and interface templates and the battle test bench are the second part (work package J), added as modules. With no
plugin and the studio never opened nothing changes: the pages, the served manifests, `welcome`, `/healthz`, the room
states and the golden results are those of §32.3. The reference is PLUGINS.md §15; the beginner's guide (Chinese)
PLUGIN-GUIDE.md; the guide for AI agents `plugins/AGENTS.md`.

**The error catalogue** (`shared/plugins/errors.js`, the plan's interface C6): every `PLUGIN_*` code — the five room
refusals of §32.3 (ERR codes, translated by the packs) and 64 codes of the checks and the studio — with `{ zh, en, fix:
{ zh, en }, doc }`, a level, a symptom for the tables and the studio's one-click fix where one exists. The checks keep
their English `problems` / `warnings` text unchanged (the logs, the tests and the tools read it) and return beside it the
same findings as `issues` — `{ level, code, text, at?, file?, params }`, `at` the path in the manifest (`['assets',
'chars', …]` for the overlay), `params` what the explanation names (`issueList()`; a check that predates the catalogue
is read as `PLUGIN_INVALID` with its text: `issuesOf`) — through `shared/plugins/manifest.js` (manifest 1 and 2, the
files), `shared/plugins/visual.js` (the overlay, the lock), `server/plugins/registry.js` (the scan: skipped entries and
warnings carry their issues; the start log adds the plain words of a skipped plugin's first problem) and
`server/plugins/pack.js`. The symptom tables of PLUGINS.md §15 (English) and PLUGIN-GUIDE.md (Chinese) are generated from
it (`node tools/plugin.mjs errors --write`). A page shows the Chinese text in a Chinese interface (zh, zh-TW) and the
English one in the others [ASSUMED: C6 defines two languages; the studio's own words are translated by the four packs].

**Schemas** (the plan's interface C7): `schemas/plugin.schema.json` (manifest 2: the fields, the class rules for scope,
parts, entry points and permissions, every part's permission, every permission used) and `schemas/overlay.schema.json`
(the asset overlay: the containers, records, files by kind, Spine models, tracks, references), JSON Schema 2020-12 —
accepted exactly when the checks find neither a problem nor a warning, on one fixture set (`test/plugins/schema.test.js`,
with a small validator of its own: `test/helpers/jsonSchema.js`); what only the checks see is named in their
descriptions (§15). The schema is stricter where the checks silently ignore a value of another type.

**The packer** moves into the server (`server/plugins/pack.js`: the folder's check, the lock with each Spine model's clip
data — `skeletonClipData`, also the preview's —, `packPlugin`, `zipPlugin`; `tools/plugin.mjs` re-exports
`checkPluginFolder` and `buildPluginLock`), because the release zips ship `server/` and not `tools/plugin.mjs`
(`tools/assets/` ships). `server/plugins/zip.js` writes deterministic zips (entries sorted, one fixed time, media stored,
the rest deflated; no ZIP64 — a plugin is ≤ 200 MB) — a zip can be pinned by its SHA-256 (the catalogue of a later step).

**The tool** (`tools/plugin.mjs`): `check` prints the plain words under each technical line (`--lang zh|en`, default
