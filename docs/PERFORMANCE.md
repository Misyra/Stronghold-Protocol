# 性能检查与优化

2026-10-05，本地 Node.js 24、Edge 无头浏览器。运行时间受硬件、JIT 和同时运行的测试影响，下面的数字只描述本机测试场景。

## 已落实

- Bot 摆阵：已选阵容的伤害覆盖、治疗覆盖和阻挡数量只累计一次，候选位置复用这些结果。每回合按单位记录缓存位置、朝向、范围及其去重签名，多个预演布局复用几何计算；下一回合使用新的模型。没有减少候选数量或战斗预演次数。
- 战斗定时器：没有任务到期时不再创建空数组，取消任务原地清理；保留时间与序号排序、回调取消、周期任务和回调中新建任务的行为。这也作用于浏览器战斗和 Bot 预演。
- 参考 xinhai-ai 分支移植共享 worker 线程池：Bot 布局预演、普通 / 联防战场接管和客户端结果复算离开主线程。线程、等待队列和任务时间均有上限，回合切换 / 退出取消任务，旧任务不能写回新回合，失败回退保留原有分片计算。严格校验等待权威结果且保留暂停结算行为；虚拟时钟和自定义 Battle 保留本地计算。预演不再记录无人消费的动画事件。
- 缓存：启动时生成代码/数据版本和独立的素材版本，URL 使用 `/_v/<版本>/…`，有效版本响应缓存一年。HTML 保持重新校验；ESM 的相对导入、绝对导入和动态导入均保持同一版本，Spine 的 atlas 和纹理继承骨骼的版本目录。
- 加载：游戏数据、战斗数据、素材清单、3D 棋盘数据不再对有版本的 URL 强制 `no-cache`；字体、图片、音频和延迟加载的渲染库也使用版本资源。普通静态宿主没有版本注入时保持原有加载行为。
- 服务端转换后的 HTML/CSS/JSON 共用有上限的响应缓存，保留 gzip、ETag、HEAD 和音频 Range；任意 `?v=` 不再触发一年缓存。文件在运行中发生变化时拒绝写入原版本的长期缓存。
- 更新检测从 HTML 注入的版本开始，避免页面加载后、第一次健康检查前恰好部署时把新版本误记成当前页面版本；局内仍然等对局结束再刷新。

## 验证

摆阵 A/B 使用原提交的 Bot 与优化后的 Bot，在 3 个种子、4 个队友、第 10 回合、5 个布局参数下比较，共 60 组布局：坐标、朝向和随机数状态一致。预热后交替测量 8 次：

| 每批 60 个布局 | 优化前 | 优化后 |
|---|---:|---:|
| 平均耗时 | 149.2 ms | 113.6 ms |

摆阵计算耗时减少约 24%。这不是整局 CPU 或画面帧率的提升比例。

`tools/botbench.mjs` 的同种子 `solo:HARD` 与 `coop4:HARD` 完整对局中，胜负、回合、生命值、漏怪、盟约、装备与晋升等记录一致，未出现错误。完整 Bot 回合仍以战斗预演为主要耗时，整体耗时变化很小；未通过降低 AI 预演质量换取速度。

浏览器验证了首页启动、真实客户端战斗模块和数据加载、刷新缓存，以及 2D 棋盘上的 Spine 加载：21 个模型全部就绪，无失败；刷新后的 92 个版本请求中 89 个由浏览器缓存返回。已有模拟性能测试包含 70 敌人 + 10 干员，以及大量敌人同时在场的场景。

回归检查包括资源命名空间、版本失效、代码更新复用素材缓存、Spine 相对路径、音频 Range、HEAD、ETag、私有文件拦截和定时器执行行为。部署和素材复制后的重启要求见 [DEPLOY.md](DEPLOY.md#15-更新)。

加入 worker 后运行 `node --test --test-concurrency=4`：3530 项通过、0 项失败、20 项跳过（全套共 3550 项，约 188 秒，包含当前工作区的匹配测试）。worker、Bot 和朝向专项另外运行 40 项，全通过。浏览器加载与刷新缓存另做了上述真实浏览器检查。

## 后续重点

- 多房间下服务器 CPU：预演已移入 worker；线程并行不减少总计算量，应按实际服务器核数和内存调节线程数，观察排队与延迟。
- 低端设备的画面：现有画质档位、2D 棋盘、Spine 内存预算与 LRU 已经存在。下一步应在实际卡顿设备测 GPU 时间、特效数量和模型动画耗时，再调整画质策略。
- 首次加载：版本缓存主要改善重复访问。首次下载仍受网络、贴图大小和音频大小影响；进一步缩减资源需同时验证透明度、Spine 图集、音质与兼容性。
- WebSocket：项目已有压缩开关、状态合并和发送节流。高并发部署应实测 CPU、连接内存和出网流量再选择压缩策略。

## 参考分支的移植与取舍

对照仓库 [xinhai-ai/Stronghold-Protocol](https://github.com/xinhai-ai/Stronghold-Protocol)，检视版本 `a759f36`。两边均为 GPL-3.0-or-later；只移植适合当前 0.1.2 的性能改动，未合入该分支的新玩法和匹配实现。

- 已移植 [worker 提交 2e89a90](https://github.com/xinhai-ai/Stronghold-Protocol/commit/2e89a90164383bf70db2815fc366912f5524c2cd) 的线程池、模拟任务、Bot 输入捕获与异步战斗接入，复用测试与基准脚本。
- 已参考 [8d5f0fb](https://github.com/xinhai-ai/Stronghold-Protocol/commit/8d5f0fba581e1e20adf71a97f2e4e55bdd1adc08) 增加平均计算时间，并修正失败 / 取消任务污染成功平均值的问题；参考 [ce5133b](https://github.com/xinhai-ai/Stronghold-Protocol/commit/ce5133b168504681336de82013dad955ce77f2a2) 加入可选 Bot 预演次数配置，默认质量不变。
- WebSocket 压缩当前已经存在，无须重复移植。容量限制原项目已有；这些限制用于保护服务，不会让单次模拟变快。
- 资源预载方案有逐文件 hash、Cache Storage 和 Service Worker，适合主动提前下载所有素材。当前已有版本 URL + HTTP 长缓存；直接复制其预载会引入第二套缓存，并且其 `/media/` 映射需要适配 `/_v/<版本>/media/`。本轮未接入，需要单独整合和验证更新失效、音频 Range 及缓存空间。
- Redis 恢复未作为性能补丁引入。CDN 在后续请求中单独接入：支持香港域名、独立的 CDN 素材版本及跨域响应，步骤见 [CDN.md](CDN.md)。

新增 worker 专项回归覆盖结果 / 时间线一致、布局评分一致、记录动画开关不影响选择、失败的本地预演回退、队列上限与优先级、取消 / 超时 / 崩溃替换、过期结果、严格 / 抽样校验、暂停以及真实 WebSocket 响应。

本机预热后运行 `node tools/workerbench.mjs --workers 4 --battles 24`，24 个真实战场的结果摘要完全一致：

| 指标 | 主线程同步逐个计算 | 4 个 worker |
|---|---:|---:|
| 总耗时 | 1692.4 ms | 633.3 ms |
| 吞吐 | 14.18 场 / 秒 | 37.90 场 / 秒 |
| 10 ms 定时器最大额外延迟 | 1682.7 ms | 10.6 ms |

这是批量计算与同步基线的比较，约 2.67 倍吞吐；旧生产路径已经使用 8 ms 分片，不能把表中的同步延迟当成旧版生产卡顿，也不能把吞吐提升当成浏览器帧率提升。共享领袖血量的实时计算和旧式服务端快照战斗不在这个基准范围内。

## CDN 接入验证

CDN 使用可配置的 `SP_ASSETS_CDN` 与可选的 `SP_ASSETS_CDN_VERSION`；服务器转换 HTML / CSS / 素材清单，浏览器动态图片与棋盘资源共用相同规则。支持普通路径的旧 CDN，以及 CDN 自己的版本路径，不使用国内服务器的版本号访问远程素材。Spine 校验已支持 http(s) 骨骼 URL。

相关回归测试 159 项（155 通过、4 跳过），静态服务、房间状态、WebSocket 与大厅集成 295 项全部通过，无失败。Edge 无头浏览器使用两个不同端口模拟游戏站 / CDN：代码和战斗数据保持在游戏站，96 个资源请求走 CDN；21 个 Spine 模型全部就绪、无失败，Bender 字体可用，71.1 秒 BGM 成功下载并解码，没有页面或 HTTP 错误。以上是本地跨域接入验证，不代表国内网络访问香港 Cloudflare 的延迟测量。
