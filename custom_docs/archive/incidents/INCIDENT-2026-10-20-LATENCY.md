# wei 入口偶发延迟尖峰排查（2026-10-20）

用户报告：`https://<节点域名>:<端口>/` 在北京时间 2026-10-19 23:00 前后偶尔卡一下，游戏显示约 1000ms。2026-10-20 00:05 起通过用户指定的 SSH 入口检查实际服务器；本次只读检查及短时探测，没有修改服务配置、重启或发布。未导出密钥、玩家身份与原始访问日志。

## 结论

**不能把问题归结为 Nginx 限速过低，也不能断言全是客户端问题。** 本机有服务端短暂停顿、宿主 CPU 争用和链路重传的证据；23:00 附近保存的服务端窗口指标尚不足以独立解释 1000ms。缺少该玩家同一时刻的浏览器卡顿与 WS RTT 记录，暂不能定唯一根因。

另有浏览器 gate 失效导致少数来源反复 WS 握手失败的问题，与已连接状态的延迟尖峰分开处理。

这些额度不会给已连接 WS 中的每个游戏消息施加 Nginx 请求速率限制。增大这些额度不是解决已连接延迟的直接办法。

22:50–23:10 按 `host=<节点域名>` 聚合访问日志，WS 有 410 次 429，来自 11 个来源，其中前三个来源分别为 113、110、110 次。多数拒绝 `rt` 约 0–2ms，`urt=-`，速率/并发均为 `PASSED`。实际 gate 片段将验证失败的非导航请求返回 429，与这些特征吻合；它们不是游戏上游处理了一秒后才返回，也不是 Nginx 速率桶耗尽。

同一日志窗口有 528 条 WS 101，但 **101 在连接结束时才记日志**，不能以 `410/(410+528)` 计算本窗口握手失败率。需要关联实际握手时间/客户端验证状态；少数连续重试来源不能直接认定是正常玩家或攻击者。

## 处理顺序

1. **先补同一时刻的证据**：客户端记录 ping 发出/收到时间、页面可见性、帧间隔及可用时的 Long Tasks，并带本机当前资源预载状态；服务端关联窗口、发送队列、存盘阶段与主机 steal。当前 UI RTT 用浏览器收到 pong 时的时钟减发出时间，包含浏览器自身消息处理延迟，不能直接称为纯网络延迟。
2. **查 gate 恢复链路**：验证失效后，客户端应能识别 gate 并恢复，而不是持续握手重试；对照 [BROWSER_GATE.md](../../operations/BROWSER_GATE.md) 的前端、gate 和 Nginx 配套版本验收。旧标签页与服务端版本需一起核对；不通过关闭 gate 或全面放宽限额掩盖问题。
3. **减轻高峰竞争**：优先落地 CDN 直取、战斗暂停排队的批量预载；已有同源 302 和大 JSON 下载确实仍在产生流量。对主线程编码、状态增量与存盘捕获分别计时，再判断需要优化哪个阶段；不根据存盘总耗时直接延长间隔。
4. **核验主机稳定性**：用相同在线规模比较 CPU steal、主线程占用及 RTT 尖峰。若持续宿主争用与尖峰重合，向供应商提交时间线并评估 CPU 更稳定的实例；四核总 CPU 不高并不能消除游戏主线程接近单核上限的压力。

不建议本次直接改 WS 超时、关闭压缩、调低持久化频率或重启 Nginx。它们都没有被当前证据证明能解决 23:00 的一秒延迟，而且可能引入断线、带宽或恢复窗口的额外代价。
