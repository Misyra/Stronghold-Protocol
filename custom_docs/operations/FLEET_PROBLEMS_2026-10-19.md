# 2026-10-19 三机问题处理方案

来源：维护机临时 `sp-fleet/PROBLEMS.md`，按 2026-10-20 仓库代码核对。数字是原记录的采样结果，本文未重新登录 A/B/C 实测；以下均为待执行方案，不是修复完成报告。部署与限额口径统一见 [DEPLOY.md](DEPLOY.md) 和 [LIMITS.md](LIMITS.md)。

## 先处理一致性与明确故障

| 原问题 | 建议处理与验收 | 代价/边界 |
|---|---|---|
| P20 B 缺 222 项及 `asset-hashes.json` | 同版发布 `data/assets.json`、`data/asset-hashes.json`、根清单及相关索引；重启后比对三机资源清单版本、条数和真实哈希 | 只同步根清单不足；避免以生产机器的不完整本地素材重新生成根清单 |
| P16 B 公告写入失败 | 核对 agent 服务用户、公告父目录写/执行权限、systemd 写目录及容器挂载；以该用户测试临时写入和原子替换，再由面板发布/撤销验收 | 需能写父目录，不能只改目标文件权限；不以 chmod 777 处理 |
| P17 xa 无 DNS | 先确认是否为对外入口，再配置对应 DNS 和 TLS，或移除废弃入口引用 | 不凭 server_name 自动创建解析 |
| P4 C 旧 worker 退出中 | 查看旧 PID 持有 WS/上游 fd，确认是否为长连接排空；持续异常再在维护窗口 restart | reload 后长连接能让旧 worker 长期存在；restart 会断线 |
| P19 残留备份 | 核验包内容、时间与回滚用途后单独清理 | 不把旧 Redis 文件或空包误当有效恢复点 |

## 降低资源链路开销

| 原问题 | 建议处理与验收 | 代价/边界 |
|---|---|---|
| P2 清单无缓存 | 仓库已提供清单缓存片段：带 query 与裸 URL 实际均兜底 15s（当前 Node 未发送旧说明中的 X-Accel-Expires）；先检查实机是否合并及 HIT | 缓存省回源 CPU，**不会减少每个完整响应的出站字节**；版本、ETag、压缩、浏览器/SW 复用才影响重复下载 |
| P1 公告无缓存 | **后续决策（2026-10-20）**：Nginx 源站只缓存 200 五秒；限流、封禁与日志仍逐请求执行，Node 计数只记回源。浏览器保持 no-store，WS 变更和运维核验使用 `?nocache=1` | 最多 5 秒的发布/撤销传播延迟；这是模板目标，仍须合并到各站配置后观察命中与延迟 |
| P6 SW 预载同源 302 | 下载地址走 CDN、CacheStorage 仍用规范同源键；覆盖 SW 和页面路径、禁 CDN 回落策略、查询哈希及 CORS 的集成测试 | 不是可无测试上线的“一行”；`allowOrigin:false` 的断路器不能被绕开 |
| P7/P8 预载抢带宽 | 后台预载先试小文件 2 车道、大文件 1 车道，战斗暂停所有排队的批量预载；屏幕即时必需资源继续按需加载 | 预载完成更慢；已在途请求可收尾，不能误停当前画面取图；先验证必备档启动依赖 |
| P5 access log 大 | 使用缓冲和有总量预算的轮转；按路径/状态统计来源，成功静态 302 可另存短保留日志 | 保留业务/WS 拒绝和 fail2ban 所需字段；“37034 条 302 占大半”需按真实行字节重算 |
| P11 本地资源不齐 | 明确 CDN 模式还是完整本地模式；按同版本补齐需要本地兜底的资源，避免部署机各自生成不完整清单 | 补本地只减少重定向，可能增加源站出站；优先修 P6 |
| P12/P15 带宽与 1.5GB 资源 | CDN 直取、按需/分组预载、ETag/哈希复用，比较完整清单和素材的真实发送量 | 增加并发不增加 22Mbps 的出口容量；减少 Nginx 回源也不等于降低发送带宽 |

## 停顿与观测

P3 的 120s 是上游读取空闲超时，不是固定连接寿命；心跳与核验方法见 [LIMITS.md](LIMITS.md#ws-超时)。

P9/P18 先补可关联的客户端帧间隔、可用时的 Long Tasks、页面可见性、资源下载状态、WS RTT/重连时刻，并对齐服务器 1s 级事件循环、存盘与 steal 时间线。采样/缓冲有上限，字段不含玩家身份；不支持 Long Tasks 的浏览器保留帧间隔采样。没有这些证据，不能把“一秒卡顿”以 99% 置信度归因客户端。

P13 先测序列化、deflate、Redis 写入各阶段耗时及主线程阻塞；将 CPU 工作移出主线程或按房间脏标记分片属于独立实现，需验证版本提交原子性、房间删除、恢复、异常重试与回滚。延长存盘间隔会扩大丢失窗口，不作为默认修复。

P14 增量帧节省带宽但消耗 CPU，现有 CPU 百分比和相关系数不足以认定因果。用同局面、同在线规模对比编码 CPU、消息字节与事件循环停顿，保留可回退开关后再优化。

P10 steal 若持续高且与停顿重叠，向供应商提交同时间线数据并评估迁移；无法只凭 steal 百分比断言宿主按某个固定比例限额。缓存与预载优化不能消除宿主 CPU 争用。

执行顺序：先 P20/P16 与配置核对，再落实现有清单缓存、日志轮转和资源直取，补观测后处理预载、存盘与实例迁移。每批单机验收再扩到三机，避免同一晚把多层限速、存储和前端同时更改而失去归因依据。
