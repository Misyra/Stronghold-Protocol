## 32. The plugin system

Unreleased. The owner decided on 2026-10-12 that the plugin system is the 0.3.0 release. Its design study (the
maintainers' notes of 2026-10-12) proposed a phased plan; the owner adopted its recommendations with the decisions
below. This chapter records what each phase changes; the reference is [PLUGINS.md](../PLUGINS.md). §32.14 records
the fixes planned for 0.2.7, which the owner folded into 0.3.0 on 2026-10-14.

### 32.1 Decisions and phases

The owner's decisions (2026-10-12):

- **MVP:** cosmetic plugins (art) and data plugins, the host's switches in the room, a content hash that every client
  checks — and **no third-party code**. Code comes later in steps, each a decision of its own: a declarative DSL, then a
  sandbox, then trusted code with the explicit consent of the server owner and of every player.
- **Position:** the original game is always the default; plugins are marked **unofficial** everywhere; plugin matches
  stay out of the statistics overview by default — those with plugins that change gameplay: a match with only cosmetic
  plugins counts as the original game (the owner's decision of 2026-10-13, §32.3); bugs seen in a plugin room go to the
  plugin's author first; no plugin
  overrides arbitrary project files; the interface word is 「插件」 (never 「模组」, which names the operators' modules).
- Everything else as the study recommended: plugins are installed on the server only and chosen by the room's host
  (gameplay) or by a player for themself (cosmetics); `plugins/<id>/plugin.json`; `packs/` keeps working; one content
  set per room with a worker per modded set; per-plugin, per-room and concurrent-set limits; incompatible gameplay
  plugins refused by default; no official files distributed through plugins.

| Phase | Content | State |
|---|---|---|
| P0 | content identity and the plugin registry, no change for players | §32.2 |
| P1a | cosmetic plugins (room and personal) | §32.3 |
| P1b | data plugins: patches, compact records, kitRef / SkillSpec operators, modes, i18n | §32.5 |
| P1c | per-room content sets: the host's 插件 panel, a worker per set, the client loading and checking `/cs/<cs>/`, the unofficial marks | §32.6 |
| P2 | DSL-lite | §32.7 |
| P3 | one script API, trusted then sandboxed | §32.10 (SDK/native), §32.11 (sandbox/Worker/CSP) |
| P4 | interface plugins: a sandboxed frame, a read-only postMessage feed, personal switches | §32.8 |
| studio | the plugin studio and the authoring tools (part 1: cosmetic plugins, the error catalogue, schemas, hot reload) | §32.9 |

### 32.2 P0 — content identity and the registry

Seen: the design study's §6.1 and its "P0 基础" list. Nothing a player sees changes; the golden results are byte for
byte unchanged (no scenario moved).

**The content hash.** `cs` names the content a room plays (`shared/plugins/identity.js`):
`sha256(canonical({ v: 1, app, sim, data, plugins, settings }))`. `sim` hashes the sorted `[path, sha256]` list of
every served `/sim/**.js` (not `nodeData.js`), `/shared/**.js` and the `/data.js` stand-in; `data` maps every gameplay
`data/<name>.json` to its hash — every file `server/data.js` loads but the presentation files `assets`, `local-assets`
(this machine's extracted art) and `emotes`, and not `data/i18n/` — so any code or data change yields a new `cs` and a
machine's own art does not. `plugins` is `[]` and `settings` `{}` for the vanilla content. `canonical` sorts keys and
drops white space; the bytes are the served bytes (a patched file, P1b: the JSON text served from memory), so a browser
hashes what it received. `shared/sha256.js` is SHA-256 in plain JavaScript: the same digests in Node and every browser,
also where `crypto.subtle` is missing (a LAN address is no secure context); the server hashes file bytes with
node:crypto and the tests check that both agree. `.gitattributes` already checks code and data out with LF, so a
Windows clone has the same `cs`. The server computes it once at start (`server/plugins/identity.js`; like the build
tag, a file changed afterwards counts from the next start) and logs `[content] vanilla <16 hex>`.

**Where it shows** (normative: design/network.md §8.4): `welcome.content { vanilla }`; `room.state.content { cs,
vanilla: true, plugins: [] }` — always the vanilla set in P0; the lobby hands `cs` to the match (`opts.cs`, the MATCH
INTERFACE), which copies it into every BattleSpec (`buildBattleSpec` keeps a well-formed `cs`, drops anything else;
`createBattleFromSpec` never reads it — a spec built without one is what it always was); `b.result.cs` is optional and
checked for its form only (the comparison is P1c's); `/healthz content { vanilla, sets: 0 }`; `GET
/cs/<16 hex>/index.json` — the manifest of the content set (every code file's hash, every data file's URL with `?v=`,
hash and size), cached for good, 404 for any other `cs`; the diagnostics' second line `content: vanilla cs=<64 hex>`
(`public/js/diag.js contentLine`; the client keeps `welcome.content` in its store; a plugin room will read `MODDED cs=…
plugins=id@version(hash)…`). The player guide's diagnostics paragraph names the line.

**The registry.** `server/plugins/registry.js` scans the language folders, `packs/` and `plugins/` and answers
`/packs/index.json` exactly as before (the language menu is unchanged), `/packs/<id>/<file>` (only what a lang
manifest names) and the new catalogue `GET /plugins/index.json` (`{ version, app, api, content: { vanilla }, plugins }`,
never cached: every plugin and pack by class with its status, the `unofficial` mark on every class but `lang`, public
manifest fields, size, file count — never a server path). `server/packs.js` is a compatibility export of it;
`shared/packs.js` keeps the language-pack index and forwards the manifest helpers (`PACK_TYPES` now carries each
type's plugin class: `assets` → `cosmetic`, `data` → `content`). Only the class `lang` loads in P0 (a lang plugin of
`plugins/` is a language entry like a pack folder in the live server's index; `tools/packs.mjs` — whose static index
could not serve a plugin's files — and `tools/i18n.mjs` keep reading the language folders and `packs/` only);
`cosmetic` and `content` plugins are checked and listed as `planned`; `script`, `ui` and `trusted` as `unsupported`,
never loaded. Folders starting with `_` (templates) and files at the top of `plugins/` are never read; a duplicate id
(across `packs/` and `plugins/`, any case) or language, a broken manifest, a disallowed file or a link inside a folder
keeps an entry out with a reason; a missing or out-of-range `requires` is a warning (P1c refuses to enable it).

**Manifest 2** (`shared/plugins/manifest.js`; reference PLUGINS.md §3–§5): `manifest: 2`, the id from the folder
(`^[a-z0-9][a-z0-9-]{1,31}$`), localized name / description, semver `version`, `app` range and `api` level (both
required but for `lang`; `PLUGIN_API = { current: 1, min: 1 }` in `shared/constants.js`), `class`, `scope` by class,
dependencies and ordering hints, typed settings (no free text), permissions that must match the parts, the parts
(`assets`, `theme`, `data`, `operators`, `enemies`, `modes`, `stages`, `dsl`, `i18n`) and entry points by class; the
file rules by class (no SVG, code only in code classes, documents never served) and the limits. Manifest 1 is read
exactly as in 0.2.0 (`readPackManifest`; `normalizeManifest` forwards to it).

**Tools, git, packages.** `node tools/plugin.mjs list` (by class, the skipped and why, the vanilla `cs`) and `check`
(manifest, files, paths, every JSON file's validity, nesting and numbers; exit 1 on a problem, `--strict` on a
warning). `.gitignore` ignores `plugins/*` but `plugins/README.md` and `plugins/_template/` (the templates come with
P1: each class's inner formats are P1a's and P1b's); the release zips ship the tracked ones (`tools/package.mjs`
`RUNTIME_DIRS`), never a server's own plugins; an update never touches them. An entry that cannot be read at all (say,
JSON nested too deep to quote back) is skipped with its reason and never stops the scan or the server's start.

[ASSUMED] — the study's own assumptions and the choices of this step, for the owner to confirm or change:

- every limit (8 MB per JSON file, nesting 64, numbers ±1e9, 200 MB and 5000 files per plugin) and `PLUGIN_API`;
- the id rule, and that `app` and `api` are required for every class but `lang`, `version` must be semver, and a
  numeric setting needs `min` and `max`;
- the presentation files left out of `cs` (`assets`, `local-assets`, `emotes`) and that every other `data/*.json`
  counts (a new gameplay file is included without a code change);
- 16 hex digits in URLs, 8 in the interface, 64 in reports; `/healthz content.sets` counts the modded sets in use;
- the registry checks manifests, file types, sizes and paths whenever it scans, but parses the JSON contents only in
  `tools/plugin.mjs check` (the content set builder of P1b parses and validates what it applies);
- a lang plugin may live in `plugins/` (manifest 2) as well as in `packs/` (manifest 1);
- a symbolic link inside a plugin folder keeps it out (a plugin folder that is itself a link is fine); dot files are
  ignored and never served.

Tests: `test/plugins/manifest.test.js`, `test/plugins/registry.test.js`, `test/plugins/identity.test.js`;
`test/diag.test.js` (the content line); still green: `test/i18n-packs.test.js`, `test/check-imports.test.js`, the
golden results. Normative lines rewritten: design/network.md §8.1 (welcome / room.state additions), §8.4 (new), §14
(BattleSpec `cs?`, `b.result { …, cs? }`).

### 32.3 P1a — cosmetic plugins

Seen: the design study's §3.1, §4.5, §6.1–§6.3, §7.1, §7.4, §7.5, §9.4 and its "P1a 外观" list. A cosmetic plugin changes
what the game shows and plays — avatars, portraits, Spine models, icons, interface pictures, voices, sound effects,
music — never a battle (the simulation reads data, not art), so a room's `cs` stays the vanilla one whatever its art.
With no plugin switched on nothing changes: the room's content is exactly P0's `{ cs, vanilla: true, plugins: [] }`, the
served manifests are byte for byte those of 0.2.6, and the golden results are unchanged (no scenario moved). The
reference is PLUGINS.md §9.

**The overlay** (`shared/plugins/visual.js`): the manifest's `assets` part, inline or a `.json` file, in the shape of
`data/assets.json` — the record containers `chars` (`avatar`, `avatarE2`, `portrait`, `portraitE2`, `spine.front`,
`spine.back`), `enemies` (`icon`, `spine`), `tokens` (`avatar`, `spine`), `bonds` / `items` / `bands` / `skills` /
`modules` / `ui` and `prof.*` (an image), `audio.bgm` (the named tracks) / `audio.bossBgm` (a track `{ loop, intro? }`,
written whole), `audio.voice` / `voiceJp` (a file or a list per slot), `audio.sfx.ui` / `battle` / `units`. A value is a path inside the
plugin folder of the field's kind (`.png .jpg .webp`, `.mp3 .ogg`), a Spine model `{ skel, atlas, textures, pma }` (the
atlas next to the skeleton with its name, the pages inside its folder) or a reference `{ "ref": "<key>" }` to the entry
of the same container in the installation's manifest — a whole record (replaced as a whole; keys beside the `ref` change
fields of it) or one field. A missing entry is a problem; another section or field is a warning and left out; nothing
but URLs and a model's clip data is ever written into the manifest. A field a plugin does not write keeps the
installation's value; a track is written whole (no installation intro before a plugin's loop); a model written for an
enemy or a token takes away its local-client model `spineLocal` (the client draws that one first) — an implied write,
never reported as an override of its own. A write to an entry the installation has needs
`assets.override`, a new entry `assets.add`. The overlay becomes a list of writes (`ops`) in the plugin's order;
resolved, a file is `/p/<id>/<8 hex>/<path>` (the first 8 hex digits of its SHA-256 — of its model's files' SHA-256s for
every file of a Spine model, so pixi-spine finds the atlas and pages beside the skeleton), a reference the entry's value
in the manifest it is resolved against (the served one). `applyOps` writes each value whole, copying the objects on the
way; `mergePluginOps` keeps the load order — the later plugin wins — and reports every path two plugins change (the
same, or one inside the other: `override { path, plugins }`). `theme` is not applied (a warning); fonts are not part of
the overlay.

**The load order** (`shared/plugins/order.js`, the study's §4.8): a plugin's `requires` join the set (`auto`) when they
may (installed, loaded, of the class and scope, in range) — else PLUGIN_DEPENDENCY; a `conflicts` in range with another
plugin of the set is PLUGIN_CONFLICT; requires / optional / loadAfter put a plugin after, loadBefore before; among the
plugins free to go, the higher `priority`, then the lower id; a cycle is PLUGIN_DEPENDENCY.

**Spine models**: their clip roles, durations, events, hit times and bounds come from `plugin.lock.json`, written by
`node tools/plugin.mjs pack <dir>`, which parses each skeleton the way `tools/fetch-assets.mjs` parses the game's
(`tools/assets/skel.mjs`, `anim-roles.mjs`; an operator's three skill slots, an enemy's numbered skills — both for a
skeleton both use), checks the atlas pages against `textures`, and adds every file's SHA-256 and size; an overlay
problem (a reference the manifest lacks) leaves the lock unwritten. A lock made from another skeleton (its SHA-256) is a
problem. The server rebuilds the lock's clip data in the shape the tool writes (`readPluginLock`: the known roles, every
clip they play an animation of the skeleton, ≤ 256 animations and 64 events, names ≤ 64 characters, durations and hit
times ≤ 600 s, bounds as four numbers; depth ≤ 64; maps without a prototype), so nothing a hand-made lock adds reaches a
browser (review of 2026-10-12: a hand-made lock used to pass any role, name or nesting through to every client, and a
deeply nested one made the room's documents fail). `tools/assets/skel.mjs parseSkel` copies a buffer that is a view into a larger one first (the Spine runtime
reads `.buffer` from its start; a small file read with `fs.readFileSync` comes from Node's pool) — the game's own models
are read as before.

**The registry** (`server/plugins/registry.js`) loads the class `cosmetic` now (`status: 'loaded'`; the pack view's
`supported` stays the lang class): when it scans it reads a cosmetic plugin's overlay and lock, checks them against this
installation's `data/assets.json` (read only when a cosmetic plugin needs it), counts what its references copy out of it
(≤ 2 MB), and hashes the files that shape it (SHA-256, kept by path + size + mtime across scans); a problem keeps the
plugin out like any other. Its folder signature now looks six levels deep (a model's files sit at
`spine/<model>/front/…`) and includes `data/assets.json`'s size and time (a manifest rewritten while the server runs is
read again). `pluginFile(id, path)` is the whitelist of `/p/`; `rescan()` reads the folders again however
they look. A catalogue entry of a loaded cosmetic plugin adds `vs` (the set of it alone) and `artBytes`.

**The visual hash** `vs = sha256(canonical({ v: 2, assets: <SHA-256 of data/assets.json>, overlays: [{ id, version, files,
writes }] }))` (the study's §6.1), `files` mapping every file that shapes a plugin's overlay — `plugin.json`, the lock, the
`assets` file, every file the overlay serves — to its SHA-256, `writes` the SHA-256 of the plugin's writes as served
(round 3, §32.3.2: `vs` pins which file goes to which slot).

**The visual sets** (`server/plugins/visualSet.js`): `resolve(ids, { scope })` — loaded cosmetic plugins of the scope,
closed and sorted, ≤ 300 MB of art and ≤ 4 MB copied by references (PLUGIN_UNKNOWN / PLUGIN_BLOCKED / PLUGIN_DEPENDENCY /
PLUGIN_CONFLICT / PLUGIN_LIMIT otherwise) — names the set by its `vs` and keeps it: a room holds its set while it uses it
(`hold` / `release`, never dropped meanwhile), of the others the 256 most recently used stay (a plugin's own set is known
from the catalogue). Its document: `GET /vs/<vs16>/overlay.json` — `{ visual: { v, vs, assets, overlays }, writes: [{ id,
ops }] }`, the composition and each plugin's writes in its own terms (paths of its folder, references, a model's clip
data), never a URL nor a copy of the art manifest; `no-cache` with the body's hash as ETag (the last 8 built are kept; a
document is built once however many ask). `GET /p/<id>/<hash8>/<path>` (`server/http/static.js`) serves only a file a loaded cosmetic
plugin's overlay names — not `plugin.json`, the lock, a document or another file of the folder, no dot file, no `..`, no
real path out of the folder (checked again when served: a link put in later is not followed) —, `immutable` at the hash
of its bytes (its own, or its model's), the current file with `no-cache` at any other (as `/assets/~<hash>/` does); a
file found changed has the registry read the folders again (at most every 5 s). In the traffic counters `/p/` counts as
assets (audio for `.mp3` / `.ogg`), `/vs/` as data.

**The room** (`server/lobby.js`, design/network.md §8.4): `room.setPlugins { plugins: [{ id, settings? }] }` — host-only,
before the match (ROOM_STARTED), in the heavy rate-limit bucket (`server/net.js HEAVY_TYPES`), and like a difficulty change
it un-readies the other humans; the same set again changes nothing, and when only its 「自动」 marks change (a plugin first
switched on automatically, now chosen) the state is broadcast without un-readying. The room holds its set in the visual
sets until it changes or the room goes. The room's content becomes `{ cs, vanilla: true, vs, plugins: [{ id, version, class: 'cosmetic', hash, auto? }],
warnings, bytes }`: `cs` stays the vanilla one, so the match receives the vanilla `cs` and its BattleSpecs are those of
the original content; an empty list brings back exactly the vanilla shape. The set is the room's: kept across its matches
and a host change. `settings` is read by the classes that have settings (none of a cosmetic plugin). New ERR codes, in
every language pack: PLUGIN_UNKNOWN, PLUGIN_BLOCKED, PLUGIN_DEPENDENCY, PLUGIN_CONFLICT, PLUGIN_LIMIT.

**The browser**: `public/js/content.js` follows `room.state.content.vs` — it fetches `/vs/<vs16>/overlay.json` as text,
parses it, checks that its composition hashes to the room's `vs` (`checkVisualDoc`) and makes it the room layer
(`public/js/assets.js` cosmetic layers: the installation's manifest → the room's set → the player's personal plugins),
composed on the manifest the page loaded itself: every plugin URL built from the composition's file table, every
reference copied out of the page's manifest, a write that does not fit left out (`shared/plugins/visual.js`
prepareVisualDoc / layVisualOps — review round 2, §32.3.1); leaving the room, or a room without plugins, takes the layer
away — one room's art never stays behind or piles up. data.js shows `assets` through the layers (`setView`), so every `data.get('assets')` of the interface, the audio and
the asset store the renderer uses (seeded with the manifest as downloaded, laying the layers over it itself) draw the
room's art; a layer change is told like a late manifest. A document that fails or will not download (two retries) leaves
the original art and says so once (a toast; an attempt is given up after 30 s). The room's top bar shows 「原版」 or
「插件 ×N」, which opens the 插件 panel (`public/js/ui/pluginPanel.js`: the server's cosmetic plugins of scope `room` with
the host's switches — read-only for the others and during a match —, versions, authors, sizes, 非官方, 「自动」, a note for
one made for other game versions, the override warnings; a room plugin the server no longer offers stays by its id, its
switch only turning it off, and is never sent again). 设置 → 外观插件 switches the server's cosmetic plugins of scope `personal` for this browser only
(`localStorage` `sp.pref.cosmetics`): each is fetched as `/vs/<vs16>/overlay.json` of its catalogue `vs` (side by side),
checked, and laid over whatever the page draws. The layers keep the manifest they make per base object (data.js's copy
and the renderer's store's may be two). The title screen says 「本服务器安装了 N 个插件」 when the catalogue lists unofficial
plugins (a button: their list, what this version does with each). The diagnostics' content line: `vanilla cs=… cosmetic
vs=… plugins=id@version(hash),…` in a room with cosmetic plugins, ` personal=id,…` for the player's own.

**Template and tools**: `plugins/_template/cosmetic/` (references only — no file of the game; the folder name is the id);
`node tools/plugin.mjs pack <dir>` (above); `check` follows a cosmetic plugin's references to the checkout's
`data/assets.json`.

**Statistics** (the owner's decision of 2026-10-13): a match whose plugins are all cosmetic plays the vanilla `cs` and
counts as the original game in the statistics overview (`room.state.content.vanilla` stays `true`) — its gameplay and
numbers are the original ones, and a player's personal cosmetics never matter; only matches with plugins that change
gameplay are left out (with P1b / P1c). Every stats record names the room's `vs` (round 2).

### 32.3.1 P1a — review round 2

An independent review (2026-10-12) found what P1a had left loose; the changes, each a decision of this step:

- **The browser composes the art itself** (it was handed a manifest the server put together): `/vs/<vs16>/overlay.json`
  carries the set's composition and each plugin's writes in the plugin's own terms (paths of its folder, references, a
  model's clip data) and no URL; `/vs/<vs16>/assets.json` is gone. The page builds every plugin URL from the
  composition's file table — the very table `vs` hashes —, copies every reference out of the manifest it loaded itself
  (`/data/assets.json`, 0.2.6's `/assets/~<hash>/` URLs), lays the plugins in the composition's load order, and leaves
  out what does not fit: a file the table lacks or of another kind than its field, a path outside the containers, a
  model out of its folder or of the lock's shape, a reference its manifest lacks (`shared/plugins/visual.js`
  prepareVisualDoc / layVisualOps; one toast per page). What it draws is exactly what `vs` names, and a room's set costs
  a few KB instead of the 1.3 MB manifest. (The point is consistency and bandwidth, not defence against the server.)
- **`/p/` serves only the very file the scan hashed**: the request `lstat`s the path — a symbolic link put in place of a
  served file after the scan is refused (404) wherever it leads, another file or a dot file of the folder included —
  and wants the real path the scan recorded (a link put in place of a folder on its way is refused too).
- **A file is the hashed one while it keeps its size, mtime, inode and ctime** (`registry.js statIdentity`): one rewritten
  with its old size and mtime put back (`rsync -t`, `touch -r`) is no longer served `immutable` under its old hash —
  `no-cache`, and the registry reads the folders again and hashes it again (its hash cache keys on all four).
- **`room.setPlugins` drops the host's result replay only when the set changed** — its `vs` or its 「自动」 marks: the
  same set again, or a refused one, leaves a settlement screen that is still open.
- **A plugin's audio is fetched without its extension**, like the installation's through `/media/` (download managers
  pop up a dialog for every fetch ending in `.mp3`): `/p/<id>/<hash8>/<path without .mp3 / .ogg>` serves the listed
  audio file of that name — of a `.mp3` and a `.ogg` of one name, the one whose hash the URL names — with the same
  whitelist and cache rules (`server/http/static.js`); `public/js/media.js mediaUrl` maps a plugin's audio URL to it and
  `public/js/audio.js` keeps its fallback to the URL with the extension. The traffic counters count it as audio.
- **A plugin file that will not load falls back, per entry**: an `<img>` of the interface (one capture listener for the
  page, `public/js/content.js`), a picture or a Spine model of the board (`public/js/assets.js` reports its own failures
  — a model not while the tab is hidden: a load the hidden tab left hanging is not the file's fault, GitHub #68), the

### 32.5 P1b — data plugins

The owner's 2026-10-13 release plan, interface C1/C2, and the adopted plugin design's §4 and §6 define this step.

unit forms), enemies, waves, stages, modes and reused items/bands/garrisons/choice effects. IDs are namespaced;

`validate.js` contains build-data's count-independent reference checks with the same diagnostic text. The builder keeps
official counts, deliberate trigger deviations, source-specific item/token assertions and the official language rule.
Content sets additionally check required fields, numeric types, finite values, paired forms, default-skill equality,
kit/effect refs and nested JSON safety. One wave, and each phase of a branch, may contain at most 64 spawn rows
(no action, or action `SPAWN`), each with an integer count from 1 to 600, and the sum of those counts may not exceed
600 (`PLUGIN_DATA_LIMIT` / `PLUGIN_DATA_REQUIRED`, `shared/plugins/limits.js`). Enemy blackboard keys named `times` or

`ammo` and `charge`. The message names the key or field, the value, the cap and the official maximum, or that the

### 32.6 P1c — room content sets

Seen: the design study's §6 (one content set per room, a match host per set: its 方案 B), §7 (the panel, the unofficial
marks), §10 「P1c」, §12 (risks) and its appendix A (the protocol increments); the 0.3.0 plan's C1 (WP-A's content set),
C3 (the room protocol) and C4 (the battle runner stays as it is: this step only adds the `cs` check). The reference is
PLUGINS.md §11; the protocol increments are `docs/design/network.md` §8.

**The room's plugins** (`server/plugins/roomSets.js`). `room.setPlugins` now takes content plugins beside the cosmetic
ones. One list is closed over its requirements and ordered (`shared/plugins/order.js`), then split by class: the cosmetic
plugins, and a content plugin's own `assets`, form the visual set (`vs`, §32.3); the content plugins form the content set
(its own `cs`). Refusals: PLUGIN_UNKNOWN, PLUGIN_BLOCKED (a class or scope rooms cannot take; the server owner's policy;
a set whose merged data does not validate — the builder's first problems as the detail), PLUGIN_DEPENDENCY /
PLUGIN_CONFLICT, PLUGIN_INCOMPATIBLE (a gameplay plugin made for other game versions or another plugin API), PLUGIN_BUSY
(one content set more than `limits.maxSets`), NOT_HOST, ROOM_STARTED. A change of the content set or of the mode
un-readies the other players like a difficulty change. `room.state.content` becomes `{ cs, vanilla: false, plugins,
warnings, bytes, dataBytes, vs?, modes?, modeId?, kittedExtra? }` and each human seat and spectator carries `content:
'loading' | 'ready' | 'failed'` — only in such a room; a vanilla room's state is byte for byte what it was.

**The content sets** (`server/plugins/contentSets.js`) adapt WP-A's C1 (`buildContentSet` / `contentSetFiles`, §32.5)
to the room: kept by `cs`, held while a room uses one, the last 8 nobody holds kept for their `/cs/` files; `hashInput`
(what a page and a match host recompute `cs` from, out of the set's index: the data hashes, the translation hashes since
WP-A's review round, the plugins and their settings) is checked against the builder's `cs` before a set is used;
`modes` are the `config.modes` records the vanilla data lacks, as `{ id, name, roomMode, difficulty }`; `kittedExtra`
the operators the set adds to a 自选 slot's list. The same plugins in the same state (each one's manifest and content
hash) with the same settings — normalized as the builder reads them (`normalizeSettings`: a key a plugin does not
declare is dropped, so it never costs a build) — are not built again: a build takes 250–430 ms of the server's thread
(measured with a plugin of one patch: 434 ms cold, 248 ms for the same set inside the builder). `limits.maxSets` is
checked before anything is built (a set no room holds while the limit is reached is refused unbuilt), and a set is
remembered only once it is kept (the review's HIGH-2: junk settings rebuilt the set on every request, after the limit
too). Until WP-A's branch was merged a stub
stood in (P1c's first commits); it is gone.

**The match hosts** (`server/match/host/`). A vanilla room's match — and a room with cosmetic plugins only, whose `cs` is
the vanilla one — runs in the server process exactly as before: the lobby still does `new MatchClass(opts)`. A content
set's matches run in one match host per `cs`, shared by the rooms that play that set: a child process
(`child_process.fork`; the default since the review, below) or, asked for with `SP_MATCH_HOST=worker`, a worker thread —
"worker" below means either. `entry.js` receives the set's
data bytes (exactly the bytes served) and its hash input, checks every file's SHA-256 and the composition against `cs`,
installs the data (`server/data.js` `setData`, new) and only then imports `Match.js`: the worker's module table — the
sim's DataSource (`nodeData.js` reads `server/data.js`), the kit and meta registries, `content/support`'s caches — is
that set's alone, built fresh in a new isolate, so nothing needs resetting. `proxy.js` is the lobby's `room.match` for
such a match: the same MATCH INTERFACE, its answers Promises, its requests answered in order. `index.js` starts a worker
on a set's first match, keeps it while it has matches and 10 minutes more, runs at most `maxWorkers` (4: a new set stops
an idle worker first, else PLUGIN_BUSY), limits each one (`resourceLimits`: 768 MB old generation, 64 MB young, 4 MB
stack) and watches it: a heartbeat every second, terminated after 10 s of silence. A worker that hangs, crashes, runs
out of memory or does not boot ends its matches with `summary.reason` 'plugin-hang' / 'plugin-crash' / 'plugin-start';
each room goes back to its lobby and its members read why (an m.toast); the log names the set and its plugins.

Measured on Node v22.22.0 (macOS; a worker thread with `maxOldGenerationSizeMb: 160`, a child process with
`--max-old-space-size=160`): in a worker thread many small objects end the worker alone (ERR_WORKER_OUT_OF_MEMORY, the
main process alive), but one large allocation can abort the **whole process** (exit 134): `new Array(4e7).fill(1)`
("CALL_AND_RETRY_LAST Allocation failed", the review's repro), and in my runs an array grown by `push` ("Reached heap
limit") and a `Map` grown by `set` — the review saw those two end at ERR_WORKER_OUT_OF_MEMORY instead, so which one
happens depends on the allocation. A child process dies alone (SIGABRT) in every case. The review found a data plugin
that reaches the `fill`: `factions.generation.minReplacedEnemyCount` 4e7 → `replacedCount` → every replaced action's
unit count → the bounty plan's `new Array(own).fill(…)` — an ordinary four-player match with a bounty. Since then
(the integration decision of 2026-10-14) a child process per set is the default and a worker thread is an opt-in
(`SP_MATCH_HOST=worker`, the `transport: 'worker'` option); and `server/match/waves.js` clamps `replacedCount`'s min / max
and the bounty plan's own units to a template action's 50 (templateSpawns' clamp; the official 1 / 5 are unchanged).
The validator bounds the `factions.generation` numbers a plugin may set since the integration (§32.5: the 10× rule, the
replaced counts within the same 50, `PLUGIN_ACTION_UNITS`). A child process starts
in about 0.2 s and holds about 117 MB (RSS) once the data and the match code are loaded (measured).

**The asynchronous lobby.** `server/net.js` answers a handler's Promise when it settles (the same `ok` / `error`
reply, the same `rid`). A room with a hosted match handles its messages and events one at a time on a queue of its own
(`Lobby.serial`): a request — `room.*` and the match's own messages alike — waits for the previous one's answer, and a
disconnect, an expiry and a resync take their turn on the same queue. A vanilla room never queues: its match answers at
once, as before. A `room.contentReady` counts only for the page that is there: one from a session whose socket is gone is answered
OK and writes nothing, and one that waited on the queue across a disconnect of its seat (each disconnect bumps the
seat's generation, captured when the message was queued) is dropped the same way — the review's MED-3: a reloaded page
was shown as checked, and could ready, before it had checked a byte. The proxy answers
a request the worker has not answered within 15 s with INTERNAL (the watchdog acts first on a living worker), and a
request still pending when its match ends is answered by the worker, not refused as WRONG_PHASE.

**The page** (`public/js/content.js`, `data.js`, `battle/runner.js`). When `room.state.content` names a gameplay set the

names no address but `/data/` and `/cs/<cs16>/`. `data.js` then shows the set (`setContent`: every screen reads its
operators, modes and texts; the server's files come back without a download when the room leaves it), the runner
simulates on it, and the page sends `room.contentReady { cs }` — again when its seat shows it not ready (a reconnect) —
or `{ cs, ok: false }` with one toast. `room.ready` waits for the player's own page, `room.start` for every player's

deadline; the authority's `b.result` carries its `cs`, and a match with gameplay plugins (`opts.requireCs`) refuses a
result naming another one like an implausible result (the server simulates the battle). A BattleSpec may carry `vs`
(diagnostics; the sim never reads it).

### 32.7 P2 DSL-lite

A declarative kit. `compileDsl(spec, { bb, chess, def })` in `server/sim/content/dsl/compile.js` returns a Kit, the same
object a kit function returns. The author reference is [PLUGIN-DSL.md](../PLUGIN-DSL.md). `schemas/dsl.schema.json` is
the closed vocabulary (C7). Prep effects compile with `server/match/dslMeta.js` (`compileDslMeta` / `registerDslMeta`)
onto a MetaRegistry the caller owns. Nothing in the sim imports the prep module, and nothing on the vanilla boot path
imports the compiler. A content plugin puts a battle spec on the compact operator as `kit.dsl` and prep specs in the
manifest `dsl` part. The builder validates a battle spec with `validateDsl` and a prep spec with `validatePrepSpec`
(`server/sim/content/dsl/validate.js`). On success the battle spec is the chess record's `dsl` (`def.raw.dsl`) and
`kitOf` calls `compileDsl`. Prep specs are kept in a builder-private map and written to `data.dsl[<plugin id>]` only
after every ordinary patch, and therefore enter `cs`. A vanilla set has no `data.dsl`. The match host
(`server/match/host/entry.js`) calls `registerDslMeta` on that process's MetaRegistry after `setData` and before
importing Match. An invalid spec does not throw from the validator; `compileDsl` throws an Error whose `.code` is
the first problem. Those `PLUGIN_DSL_*` codes are in the error catalogue (`shared/plugins/errors.js`). A direct
literal past the official cap uses the existing `PLUGIN_DATA_BOUND`.

The battle vocabulary is the design study's list: triggers `always / deploy / battleStart / attack / hitDealt /
hitTaken / kill / allyDeath / skillStart / skillEnd / every / hpBelow`, conditions `chance / targetHas / selfHpBelow /
enemiesInRange / bondActive / skillActive`, actions `buff / status / damage / heal / sp / dp / push / pull /
spawnToken / layers / shield / fx`, values as numbers or `{bb}` / `{talent:[i,key]}` / `{mul|add|min|max}`, targets
`self / target / source / alliesInRange / enemiesInRange / enemiesInRadius / lowestHpAlly / allAllies`. Only
addition, subtraction, multiplication and division. No loops and no state outside the battle. Damage this compiler
deals carries a `dsl` tag, and a DSL `hitDealt` / `hitTaken` handler ignores that tag (SIM.md §5).

Prep triggers `roundStart / income / buy / sell / refresh / merge / levelUp / battleResult` map to `onRoundStart /
onIncome / onBuy / onSold / onRefresh / onMerge / onLevelUp / onBattleResult`. Actions `funds / layers / gainItem` call
`addFunds` / `addLayers` / `grantItem`.

### 32.8 P4 — interface plugins

An interface plugin is a page the server serves and the player's own browser shows. It does not join a room's
`plugins[]`, it sends no protocol message, and it cannot play the match. The word in the interface is 「插件」.

**What loads.** Class `ui` is `supported`, so the registry lists it `loaded` (`shared/plugins/manifest.js`). `script`
and `trusted` stay unsupported. A ui manifest names `entry.client` (an `.html` file; permission `ui.frame`) and
`slots` — `hud.right`, `result.tab`, `stats.tab`, `room.panel` (`UI_SLOT_IDS`). An absent or empty `slots` is a
warning and the plugin still loads; the host grants it no slot. A bad list, a duplicate, more than those four, or
`slots` on another class, is a problem. `description` is the 简介. The frame files (`.html`, `.js`, `.css`, `.png`)
must sit under the directory of `entry.client`. A folder whose name starts with `_` is never scanned;
`plugins/_template/ui/` is the example (a damage tally) and is copied by a server owner under a real id.

**Serving and `vs`.** The registry (`readUiFrame` in `server/plugins/registry.js`) hashes the frame files the way a
cosmetic overlay is hashed and names the plugin with `visualHashOf` (`shared/plugins/visual.js` — not a second hash).
`writes` is the canonical `{ entry, slots }`; `plugin.json` is in the composition, so editing the manifest changes
`vs`, and is not served. The catalogue entry of a loaded ui plugin adds `slots`, `entry` (a path inside the plugin),
`vs`, `frameBytes` and `frameFiles` (`{ path: sha256 }`). It does not add `artBytes` and it is not a visual set: a
room's `resolve` still accepts only cosmetic ids (`PLUGIN_BLOCKED` for a ui id). The files are served at
`/p/<id>/<hash8>/<path>` with the same traversal, symlink, identity and hash8 rules as cosmetic art. Responses of a
ui plugin's files, and only those, carry `Content-Security-Policy: ` the string `UI_FRAME_CSP`, on 200, 206 and
304 (one header object). There is no site-wide CSP (that stays P3b). A 416 is an empty body and does not carry it.

**`cs`.** A ui plugin is not an input of `cs`. Installing one, or editing its page, does not change `cs` of a build.
`cs` does hash every served `/shared/**.js`, so this phase's new `shared/plugins/ui.js` (and any edit of
`shared/plugins/identity.js`) changes the vanilla `cs` relative to the parent commit. Relative to the same build with
`plugins: []` and no ui folder, the hash is unchanged. Golden results are untouched.

**The frame.** The host sets an iframe
`sandbox="allow-scripts"` (no `allow-same-origin`: the origin is the string `"null"`), `referrerpolicy="no-referrer"`,
`allow=""`. [ASSUMED] `credentialless` is set with `setAttribute` where the browser has it. The iframe's `src` is the
plugin's own `/p/<id>/<hash8>/<entry>` (`framePageUrl`, checked by `frameEntryAllowed`). The host counts loads
(`frameLoadDecision`): the first is the entry, and any later one destroys the iframe, clears `ready` and posts nothing
further. Moving the iframe between the park and a slot makes the browser reload it from its `src` (the entry), so a
move the host makes itself (`moveFrame`) resets the count and `ready` first; a navigation the plugin starts is never
such a move. (The review round first used a redirect page, `plugin-frame.html`, that navigated from its own load handler;
Chrome gives no iframe `load` event for such a page, so the entry looked like the redirect, never got `welcome` and
never took its slot — the browser test caught it. The redirect is gone; the response header and the iframe attribute
already sandbox the page.) A plugin message is
applied on the next turn, so a `load` that was already queued runs first. `ready` is accepted only while the count is
still the entry. `targetOrigin '*'` is required because the origin is the string `"null"`, and `"null"` does not tell
the entry document from a later opaque document — changing it is not a substitute for stopping the feed. The host
accepts a message only from that iframe's window and only when `event.origin === 'null'`. Slot elements use an empty
`dangerouslySetInnerHTML` so a Preact re-render does not remove the foreign iframe. A frame that a re-render detaches
is parked and put back; a frame the host itself moved stays where it was moved.

`UI_FRAME_CSP` includes `sandbox allow-scripts` (no `allow-same-origin`), `frame-ancestors 'self'`, `base-uri 'none'`
and `form-action 'none'`. A `<meta>` sandbox is ignored, so the response header is what sandboxes the document when
the same URL is opened at the top level (`/p/<id>/<hash8>/<entry>.html`, or the redirect above). The hash is not a
gate: any 8 hex digits still answer 200 with `no-cache` and this header. Do not add `allow-same-origin` to make
`'self'` match the opaque origin.

### 32.12 Forge pack import

The owner's decision of 2026-10-13 (the 0.3.0 plan, work package H): a Forge workshop pack — the community fork's
format, not its code — can be imported as the plugins it can become. The importer is original. Forge is
GPL-3.0-or-later; nothing was copied from it, so `THIRD-PARTY-NOTICES` gains no row. The importer does not screen
for official art, the same rule as the packer. The reference is PLUGINS.md §16. The beginner's steps are
PLUGIN-GUIDE.md, 「从 Forge 包导入」.

**The tool** (`server/plugins/forgeImport.js`, `tools/plugin.mjs import-forge <dir|zip> [--out] [--id] [--dry-run]
[--json]`): reads `pack.json` and the files it names. Skins, portraits, avatars, icons and Spine become a cosmetic
overlay, a `{ ref }` when that is what the overlay already uses. Voice, music and sound effects become audio in that
overlay when the key is one this game already has: `voices` to `audio.voiceJp`, `voiceLangs.cn` to `audio.voice`,
bgm tracks `lobby|prep|combat|unite|boss`, `bossBgm` as `{ loop }`, and `sfx.ui` / `sfx.battle` / `sfx.units` in the
overlay's shape. Numeric edits, new operators and new enemies with an official base become a content plugin
(patches and compact records). A skill script is never executed: the operator gets kit `"generic"` unless a JSON
object passes `validateSkillSpec` (`kit.spec`). No DSL part is written. A flat UI translation becomes a lang plugin.
A version-1 content translation is kept only when every leaf replaces an existing string. Announcements and credits
become `description` and `credits`. A `client.panels` entry becomes a ui stub only for `screen.game.hud` and
`screen.game.aside` (`hud.right`) and `screen.result.footer` (`result.tab`), and only when it does not wrap a
component and is not marked read-only false. The stub tells the author to rewrite it to postMessage API v1. The
panel script is not copied. `stats.tab` and `room.panel` have no Forge mount yet. Engine replacement, protocol,
server logic and any script are not imported. Each is one reason in Chinese and in English. There is no
`buildVisualSet`. A cosmetic product is checked with `createVisualSets({ registry }).resolve`, a content product
with `buildContentSet`. A problem or a warning fails the import and the destination is not left.
`IMPORT-REPORT.md` is written into the primary folder after `pack` succeeds.

**The studio.** `/studio/` grows one button, 「从 Forge 包导入」: pick a zip or a folder, read the report, confirm,
and the plugins are written under `plugins/`. While the browser is still reading the file, preview and confirm stay
disabled, the previous report is cleared, and a late read cannot restore it. The request body is `{ zip?: base64, files?: [{ name, data: base64 }],
id? }` (`POST /studio/api/forge/preview`, `POST /studio/api/forge/import`). It is never a path on the server. The
gate and the studio key are the ones §32.9 already requires. The new strings go through `t()` and are in the four
language packs.

**Safety.** Packs are untrusted. The reader is this module's own. It uses `crc32` from `server/plugins/zip.js` and
does not call `unzipFiles`, which has no path or size guard. It rejects path traversal, symbolic links, ZIP64,
encryption, a data descriptor, more files than `PLUGIN_LIMITS.files`, and a declared or inflated size over
`PLUGIN_LIMITS.pluginBytes`. ZIP64 is recognised from the EOCD sentinel, a ZIP64 extra field, or a ZIP64 locator in
the 20 bytes immediately before a real EOCD. A `PK\\x06\\x06` inside an entry is not treated as ZIP64. A raw zip
larger than `PLUGIN_LIMITS.pluginBytes` plus 64 KiB is refused before it is read. JSON uses `checkJsonLimits` and
refuses the keys `__proto__`, `constructor` and `prototype` before any mapping. Asset trees are null-prototype
objects, and a path is walked only through own properties. A directory read uses `lstat`, does not follow a link,
refuses a regular file with `nlink > 1`, opens with `O_NOFOLLOW`, and checks `fstat` before reading. Empty
directories count toward the file cap. A dry run stages under the temporary directory and deletes the stage. A real
write stages in a dot directory beside `plugins/` (the registry skips dot directories) and commits by rename on that
same filesystem. `EXDEV` is a failure: the import does not copy. A failed commit removes only destinations that
attempt created. The stage is always removed. The visual set and the content set are built from a temporary view
that can see plugins already installed and the staged products. The source pack is not linked into that view.

**Errors.** `PLUGIN_FORGE_INPUT`, `PLUGIN_FORGE_ZIP`, `PLUGIN_FORGE_JSON`, `PLUGIN_FORGE_ID`,

### 32.13 The catalogue and the frozen plugin API

The owner's decision for 0.3.0 (the plan's C8, work package I): a community list is a document format and a tool, not a
service. This project does not host plugins and does not run a market. `mod-system.md` §8.2 ("local files only, no
network") is superseded here: an address install is https, and the zip is pinned by SHA-256.

**Catalogue.** `schemas/catalog.schema.json` and `shared/plugins/catalog.js` read `{ "catalog": 1, "name", "plugins":
[{ "id", "name", "version", "class", "description", "url", "sha256", "bytes", "homepage", "license", "authors", "app" }] }`.
`url` is https with a dotted host and no user or password. `sha256` is the zip. Unknown fields are problems, so the
schema and the check agree on one fixture set (`test/plugins/catalog.test.js`), including the same id on two different
entries and an `app` that is not a version range. The schema's `uniqueItemProperties: ["id"]` is not a stock JSON
Schema keyword: `test/helpers/jsonSchema.js` enforces it, and a stock editor that ignores the keyword will not see a
duplicate id. The normative check is that validator plus `readCatalog`. A missing `app` is compatible. An empty or
whitespace-only `app` is invalid, and `entryStatus` reports it incompatible (an unreadable range is not treated as a
match). `docs/plugin-catalog.example.json` points at `example.invalid` and is documentation only.

**Install.** `node tools/plugin.mjs install` and `POST /studio/api/catalog/install` share `server/plugins/install.js`.
A local zip installs as it is. A Windows drive (`C:/…`, `C:\…`) and a UNC path (`\\server\…` or `//server/…`) are files,
not addresses. An https URL requires the hash. The bytes are checked with SHA-256. The download stops at
`PLUGIN_LIMITS.pluginBytes` (200 MB), including a `Content-Length` over the cap and a body that grows past it. One
deadline covers DNS, every redirect and the body (60 s for a zip, 20 s for a catalogue document); it is not reset on
each hop. Redirects use `redirect: 'manual'`. Each hop, including the first, must be https on port 443 with no user
info, and the destination must be public: the literal address after `new URL` (short, octal, hex and decimal IPv4 are
folded first) and, on the connection, every address the name resolves to. Loopback, private, link-local, CGNAT,
multicast, unspecified, documentation and IPv4-mapped IPv6 addresses are refused, as are `.local` and `.localhost`.
The production transport is `https.request` with a lookup that classifies those addresses before it returns any of
them, so the socket is not connected to one it refused. An injected `fetch` with no `lookup` (the tests) still checks
the literal address and the port, and does not resolve. The operator allowlist is `SP_PLUGIN_DOWNLOAD_ALLOW` and
`plugins/config.json` `allowDownloadHosts` (exact host, or `host:port`; IPv6 only as `[addr]` or `[addr]:port`; no
wildcards; default empty). A matching entry permits that host's port and a non-public resolution of that name. A
catalogue document cannot add itself. A missing, unreadable or wrong-typed `allowDownloadHosts` adds nothing, and a
public download still works. `policy.js` ignores the key. The zip is read by `readPluginZip`
(`server/plugins/zip.js`), which `unzipFiles` does not replace: encrypted entries, data descriptors, ZIP64 (a central or
local extra id `0x0001`, a version-needed of 45 or more, a ZIP64 locator, or a `0xffffffff` size), symbolic links, any
other non-file, path traversal, duplicate names, two paths that differ only by the case of a segment, a path that is
both a file and a folder, more than `PLUGIN_LIMITS.files` entries, and a declared uncompressed or compressed size over
the cap are refused before inflate and before `plugins/_incoming/`. The tree is written under
`plugins/_incoming/<random>/<id>/` without following a symbolic link, `checkPluginFolder` must report no problem (a
warning does not stop the install), and the folder is then renamed to `plugins/<id>/`. The same id is not overwritten
unless `force`: the old folder, or the symbolic link if the id is a link, is renamed to `plugins/_replaced/<id>-<UTC
stamp>/` and is not deleted. A failed check deletes only the temporary folder. No file of the package is imported,
spawned or otherwise run. The studio page 「从目录安装」 posts a catalogue URL or the text of a file the browser read.
It does not download the zip. The server does, on this machine and the LAN, with the studio key. A path on the server's
disk is not accepted from the browser. `server/index.js` passes `opts.fetch` into the studio so a test injects the
download and never touches the public network.

**Frozen table.** `docs/PLUGIN-API.md` and `shared/plugins/surface.js` name every member of the closed sets: manifest
fields, permissions, classes, patch operations, compact-record fields, overlay leaves, the DSL vocabulary (passed in;

the prose rather than as a fourth stability), error codes, catalogue fields, `sp:sdk@1` (experimental: its members

### 32.14.2 Official scene lighting after the client's shader (#549, PR #571)

GitHub #549 (PR #571 by @andrew05060414). Seen: after 0.2.6 set `SCENE_LIGHT.direct` / `.indirect` to 1 (§31.7) the
official battlefield scenes are still darker than the client and flat — no sand ripples, black shadows. 0.2.5
(gains 0.8 / 0.4) measured about half the client's brightness; 0.2.6 was not measured for this note.

Cause: the client renders in gamma colour space (PlayerSettings `m_ActiveColorSpace` 0, LDR camera; read from the PC
client's `globalgamemanagers`, Unity 2021.3.39f1), so Unity adds the baked light (RGBM pages, `m_LightmapFormat` 2,
read as 5 · A · RGB) and the key light (Mixed / Shadowmask) in display values, while `sceneMaterial` added them in
linear light. The official GLES program of `Torappu/Scene/StandardRealtimeShadow`
(`shaders/standardrealtimeshadow.ab` of the Android version `26-04-13-12-31-42_e9b560`, the variant with the sand
material's keywords) confirms the gamma-space sum and the RGBM read, and has three more terms that were not drawn.

Now:
- `sceneMaterial` follows that program: diffuse = albedo × 0.779 · (1 − metallic), lit by the lightmap and by the key
  light · N·L · the baked shadow; the key light's specular highlight; the reflection of the scene's default reflection
  cubemap by roughness and Fresnel (from 0.221); N bent by the normal map; all in display values, clamped to 1.
  `SCENE_LIGHT`: `range` 3.0, `ambient` 0.5, `direct` 1, `indirect` 1.
- The baked shadow is used whole: `_ShadowStrength` scales only the units' realtime shadow map, which is not drawn.
- `scenes.py decode_rgbm` writes the pages as 5 · A · RGB / 3.0 with scene.json `lightEncoding: 'gamma'`; it adds to
  each scene the decoded reflection atlas `env.png` (scene.json `env`) and to `scene/tex` the materials' normal and
  metallic-gloss maps. The atlas is the cubemap the client binds as `unity_SpecCube0`: the baked texture of the
  ReflectionProbe whose box holds the board, at the probe's intensity (act2autochess_m01: box 40, 0.8; m03: box 50,
  0.6; every renderer there blends probes), else the default reflection of RenderSettings at the scene's reflection
  intensity (the other nine scenes, which share one cubemap; `env.source` says which). The cubemap data is
  face-major (each face with its mip chain) and RGBM (texture usage 5): each face's mip 0, box-downsampled, differs
  from its own mip 1 by 4–9 of 255 and from the other faces' by 24–42; two faces of the shared cubemap (+Y and −Z)
  are byte-identical in the asset. In these scenes Unity −Z is up, and the probe atlases of m01 / m03 have the sky
  on the −Z face and on the −Z side of the four faces around it, as the shader's lookup expects. The 11 scenes have to be extracted again (`node tools/setup.mjs --scenes`) and the full zip
  rebuilt for the exact result.
- A scene extracted earlier still draws: without `lightEncoding` through the `SCENE_LM_V1` read-back, without `env`
  as the plain sum albedo × (lightmap + key light · N·L · shadow).
- The focus falloff outside the lit field rect stays (`uFocusDim` 0.72, owner decision 2026-10-12: the client has
  none).

Measured on act2autochess_m02, prep camera, 0–255, against a client screenshot of another framing (like places, not
the same pixels); "before" is 0.2.5:

| place | 0.2.5 | now | client |
| --- | --- | --- | --- |
| light stone tiles | 107 | 186 | ≈ 186 |
| planks | 108 | 203 | ≈ 206 |
| sand left of the field (under the focus falloff) | 97 | 164 | ≈ 183 |

**[ASSUMED]** (inferred, not read from the client; marked in `materials.js SCENE_LIGHT` and `scenes.py`):
- `SCENE_LM_V1`: the pages of an earlier extraction hold (L_linear / 8)^(1/2.2) per channel; the shader rebuilds the
  display value approximately (a few percent bright).
- The tangent frame of the normal map comes from screen-space derivatives, t along +u and b along +v (scene.bin has
  no tangents); the bump's sign was not checked against the client surface by surface.
- One reflection cubemap per scene, chosen at the board's anchor: a renderer outside the probe's box (far
  background) would show the default reflection in the client, and the blend at the box's edge is not reproduced.
- The reflection's azimuth against the board follows from uploading the faces in stored order and looking them up
  with the Unity-space direction; checked only by where the sky sits (below), not against a client screenshot.
- The vertex-colour blend is left out on the reading that it is a tile buried in sand
  (`mix(albedo, _BlendColor, smoothstep(colour.r) · _BlendStrength)`), which the client uncovers at run time by a rule
  not found yet; drawn as written it covers every patterned tile of the field.
- `ambient` 0.5: the light of a mesh without a lightmap page.

Still not done: emission maps, the units' realtime shadow, map effects (`mapeff_*`), the post-processing profile, the
water (PR #555; subsequently ported in §32.14.6). No gameplay change; golden results are not moved.

Tests: `test/render/board3d-scene.test.js` (the decode, the material's uniforms and defines for both page encodings).

### 32.14.5 Bots: medic placement, purchases by hand capacity, rehearsals with the real battle inputs (#577, #315; ideas from PRs #606 / #607 / #608)

The maintainer approved all three ports on 2026-10-14. Sources: [#577](https://github.com/sganggs/Stronghold-Protocol/issues/577),
[PR #606](https://github.com/sganggs/Stronghold-Protocol/pull/606), [PR #607](https://github.com/sganggs/Stronghold-Protocol/pull/607)
and [PR #608](https://github.com/sganggs/Stronghold-Protocol/pull/608), reviewed against the current bot and §32.14.1.
All selection preferences below are [ASSUMED] bot policies tracked in [#315](https://github.com/sganggs/Stronghold-Protocol/issues/315),
not changes to official combat rules. Normative: DESIGN §6.6; implementation reference: META §1.5 and §2.2.

Blocking medics prefer off-road positions, then supported road positions, with a legal fallback on a crowded board.
The guard repair and medic placement share `supportedContact`: every ground entrance needs allied damage covering
both the occupied tile and its preceding contact; different entrances may have different supporters. Boss medics
with wider healing ranges go first; equal exposure scores prefer allied damage not already covered by a placed
medic. This differs from PR #606's total-DPS tie-break, which could concentrate two medics on the same damage group.

Lineup scores count withdrawn BOARD_AND_DECK members only while actual hand capacity permits keeping them. The
purchase probe reserves the new operator's hand slot before withdrawals; deployment frees slots only afterwards.
Purchase scores within `1e-9` prefer the cheaper offer. Pre-emptive hand shedding requires an owned roster larger
than the deploy cap. The existing arrangement-improvement thresholds stay unchanged.

Rehearsal reuses normal battle inputs, the normal field seed, battle-start hooks, enemy replacements, teammate effects
and battle layer gains. Each candidate clones the current meta RNG. Unlike PR #608, isolation is enforced by the
context boundary: state writers are no-ops, reads/source/event objects are detached, teammate/player contexts are
restricted too, and a separate dispatcher owns script budget and error handling. The candidate board never replaces
the live board; no recompute side effects, preview settlement or live diagnostics occur. Actual combat keeps the
original dispatch and random stream. A preview cannot predict later preparation or other players' random choices.

Regressions cover real medic battles, split boss healing, every incoming contact, capacity-aware purchases, actual
battle/rehearsal ranking, zero-state RNG cloning, and intentional state-writing/erroring official and plugin handlers.
The retained new `coop2-NORMAL-1-unowned-roster` golden reliably exercises stand-ins irrespective of purchases;
previous stand-in scenarios remain outcome regressions. Match goldens are regenerated for changed bot decisions and
subsequent combat/economy (17 of the 20 earlier match scenarios move, every one with its team's rounds passed
unchanged). A fixed-seed comparison of 56 bot matches against the §32.14.1 base: teams 8 better / 42 equal / 6 worse
(+2 rounds), players 19 better / 103 equal / 22 worse (−8 rounds) — a policy trade-off, not tuned to those seeds.
The already integrated lobby and docs-path stability changes are not reapplied.

### 32.14.6 Official scene water (#549, idea from PR #555)

GitHub #549 (PR #555 by @xcdoge). The owner took the water into 0.3.0 on 2026-10-14, ported onto §32.14.2's

Now:
- The board's water tiles and the scenes' water surfaces share `materials.js waterMaterial`, with the active map's own
  record: deep / shallow colours, normal tiling and strength, two scroll speeds, caustics, sun direction, glossiness,
  colour and sky intensity. A surface is recognised by a shader ending `/StylizedWater`, then a `_water<digits>`
  material name — no material name is hard-coded. Several surfaces keep their own records (act1 m05 / act2 m04 have
  a second, yellow-green one); **[ASSUMED]** the board's tiles take the first. `DynamicWaterTile` is a platform decal,
  not a surface: it keeps its own shader (`sceneWaterDecalMaterial`) and never selects the board's water.
- The colour space follows #571: water colour, reflection, highlight and caustics are summed in display (gamma)
  values, clamped, turned linear once (exact sRGB), dimmed by the shared focus falloff and encoded by
  `<colorspace_fragment>`. PR #555's `pow(rgb, 2.2)` followed by sums in linear light is not used.
- The reflection is the scene's decoded cubemap (#571's `env`: the same lookup with board z negated, its range and
  mip count) when the scene has one; only without it the PR's two-stop sky gradient — never both. The board's
  water follows the active, successfully built scene and returns to its defaults for another map, a removed scene
  or no stage; a preloaded scene of another stage does not recolour it.
- Without an official scene the procedural board keeps its old water (`WATER_DEFAULTS`: the old colours in display
  values, motion, sun and fixed view, exponent 40, alpha 0.9; within 10/255 of the old formula, unit-tested).
  `sceneMaterial`, `SCENE_LIGHT` and `sceneEnvTexture` are unchanged.

highlight gain 0.6 / 1.6, caustics gain 0.2 / 0.35, alpha lift 0.2; the deep / shallow blend `0.08 + 0.2 · N·L`
